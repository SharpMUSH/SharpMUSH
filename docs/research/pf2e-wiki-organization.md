# Give PF2e Readers Clear Navigable Context

SharpMUSH should present **Pathfinder 2e Remaster as a coherent reference collection beside the game's own wiki**, with an authored landing, recognizable rules topics and scoped search. Collections should separate ownership and context; namespaces should continue to describe page purpose; categories should connect related subjects; structured fields should support comparison. These are different responsibilities. The imported **4,711 pages and 130 category pages** make the distinction practical: moving the same flat taxonomy behind one collection link reduces global clutter but does not create an understandable rules reference. The package already contains authored ancestry and feat indexes worth preserving. Its existing four pins and the current collection-browser implementation are useful starting mechanisms, not the final information architecture. ([Pinned package and inventory proposal](https://github.com/SharpMUSH/SharpMUSH.Packages/tree/2659a733a4519b76e64a727be2687794afc04f6b/pf2e-remaster))

## Separate page identity from the ways readers browse

MediaWiki offers a useful distinction, without being an implementation specification for SharpMUSH. Its namespaces identify page purpose and behavior, while categories provide explanatory pages and generated membership. Categories form a graph, including multiple parents, rather than necessarily one strict tree. Subpages express explicit parent/child titles when enabled; arbitrary slashes do not automatically establish that relationship. These mechanisms should not be collapsed into a single PF2e namespace or a title-prefix convention. ([Namespaces](https://www.mediawiki.org/wiki/Help:Namespaces), [Categories](https://www.mediawiki.org/wiki/Help:Categories), [Subpages](https://www.mediawiki.org/wiki/Help:Subpages))

The recommended SharpMUSH model is a stable collection identity alongside the existing namespace and page identity. That allows a PF2e rules article, a PF2e category introduction and its licensing/help material to retain distinct purposes. Ultimately, a game's own Conditions page must coexist with a PF2e Conditions page without accidental membership mixing. **Package ownership can identify the collection, but filtering package-owned IDs does not itself establish independent canonical names.** MediaWiki's custom-namespace documentation illustrates why identity changes require migration, not merely a different label. ([Custom namespaces and existing pages](https://www.mediawiki.org/wiki/Manual:Using_custom_namespaces))

| Concern | Recommended meaning in SharpMUSH | Example or boundary |
| --- | --- | --- |
| Collection | Stable ownership and reference context | Game wiki; Pathfinder 2e Remaster |
| Namespace | Page purpose | Main article, Category introduction, Help/licensing page |
| Content kind | Structured gameplay entity, when known | Ancestry, heritage, class, feat, spell, condition |
| Category graph | Human topics and related membership within a collection | Character creation → ancestries; class → its feat index |
| Subpage | Explicitly authored parent/child document | A guide and its walkthrough, not every spell's taxonomy |
| Facet | A reliably populated independent comparison field | Spell tradition/rank; item level/price; feat level |
| Source/version | Provenance and rules version, distinct from topic | Book/page, imported revision, Remaster/Legacy relationship |

This table is a **SharpMUSH recommendation**, informed by MediaWiki's separate organizational mechanisms and AoN's content-specific indexes; it is not a claim that either reference implements SharpMUSH collections. ([MediaWiki categories](https://www.mediawiki.org/wiki/Help:Categories), [AoN spells](https://2e.aonprd.com/Spells.aspx), [AoN sources](https://2e.aonprd.com/Sources.aspx))

## Make the landing answer player and GM questions

Archives of Nethys exposes recognizable groups such as Character Creation, Equipment, Feats, Game Mastery, Rules and Spells/Rituals. Its Human pages retain adjacent details, heritage and feat routes; class entries lead to class-specific feats. Conditions provide relationship groups and a route back to their index. These are observed navigation patterns, not proof that SharpMUSH should copy AoN's whole interface. ([AoN navigation](https://2e.aonprd.com/), [Human heritages](https://2e.aonprd.com/Heritages.aspx?Ancestry=64), [Classes](https://2e.aonprd.com/Classes.aspx), [Conditions](https://2e.aonprd.com/Conditions.aspx))

A practical PF2e landing should start with a readable collection name, a short explanation of the imported snapshot and **Search PF2e Remaster**. Its principal groups should address **Build a character**, **Play and look up rules**, **Spells**, **Equipment**, and **Run a game**. Character creation should expose ancestries/heritages, backgrounds, classes/archetypes, feats and skills. Rules should expose actions, conditions and traits. GM reference should lead to creatures, hazards and difficulty classes. Source information and an exhaustive directory belong in supporting routes. Exact labels and membership require checking the installed pack; these groups are proposals, not a mandated new taxonomy.

Use brief descriptions and direct links within each group. A landing must help readers choose, while allowing knowledgeable readers to bypass it. NN/G's category-page research supports contextual landings for large, complex inventories and warns that unnecessary intermediate pages obstruct known-item retrieval. Its evidence is mainly ecommerce, so the transfer to a rules reference needs task testing. ([Traditional and hybrid category pages](https://www.nngroup.com/articles/category-pages/))

The first acceptance journeys should be concrete: enter the collection, find an ancestry, open its heritage index, and return to the ancestry; find Alchemist feats grouped by level; look up Blinded within PF2e; then return to the game's setting without passing through PF2e categories. These test the relationships already identified in the package, rather than merely verifying that every title can eventually be paged to. The complete category directory remains valuable for expert exploration. **A 130-peer card grid or 130 collapsed sections should not be the collection's front door.** Long menus need grouping, but excessive nesting also damages discovery; no research establishes a magic maximum number of categories for this pack. ([Hierarchy tradeoffs](https://www.nngroup.com/articles/flat-vs-deep-hierarchy/))

## Let search refine the reference without hiding its structure

Name lookup and comparison need different interfaces. AoN offers feat views grouped by level, spell views organized by tradition/rank, and equipment families with relevant comparison columns. Its linked table configurations and developer implementation substantiate this model; the research did not exercise every live filter. These are stronger models for rules discovery than one universal alphabetical list. ([Feats](https://2e.aonprd.com/Feats.aspx), [Spells](https://2e.aonprd.com/Spells.aspx), [Equipment](https://2e.aonprd.com/Equipment.aspx), [Search implementation](https://github.com/galdiuz/nethys-search))

SharpMUSH should initially preserve authored hubs and trustworthy category relations. Add class/feat level, spell tradition/rank, item category/level/price and source filters **only after measuring structured metadata coverage**. Facets require maintained metadata and impose interaction costs; plausible controls backed by incomplete prose extraction would hide valid results. Filter labels should match the distinctions readers actually use. ([Filters versus facets](https://www.nngroup.com/articles/filters-vs-facets/), [Helpful filter categories](https://www.nngroup.com/articles/filter-categories-values/))

The current first-phase implementation searches localized/source **titles and category labels**; it does not provide body search or the structured facets above. It derives membership from durable package page IDs while existing global namespace/slug identity remains authoritative. Its tested counting, pagination and permission mechanics should support the next layer of navigation, not be described as completing namespacing or rules discovery.

Keep search, source selection, active category and pagination in recoverable URL context. Articles need an intelligible return path. A breadcrumb should show known structural parents, such as Wiki → Pathfinder 2e Remaster → authored section → article; choosing an arbitrary category from a multi-category article would invent a false hierarchy. Collection → article is an honest fallback, with related topics separately linked. WAI recommends complementary search and structural routes and specifies labelled breadcrumb navigation. ([Multiple ways](https://www.w3.org/WAI/tutorials/menus/multiple-ways/), [Breadcrumb pattern](https://www.w3.org/WAI/ARIA/apg/patterns/breadcrumb/))

Ordinary navigation should use semantic links and disclosure controls rather than application-menu roles. Keep main choices visible; GOV.UK cautions that accordions hide information and should not contain universally needed content or nested accordions. Validate meaningful keyboard order, 320-CSS-pixel reflow, appropriately sized targets, and accessible result-count announcements. Brief search status should be announced without reading every result or moving focus on every keystroke. ([Disclosure navigation](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/), [Accordion guidance](https://design-system.service.gov.uk/components/accordion/), [Focus order](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html), [Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [Target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [Status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html))

## Preserve identities, permissions and provenance through updates

Qualified identity requires a separate migration contract. Inventory existing IDs, ownership, category edges, translations, inbound links, requirements and local edits before changing canonical keys. Produce a dry-run collision report, preserve IDs/history, and retain unambiguous legacy aliases. Ambiguous old names need an explicit resolution, not arbitrary reassignment. MediaWiki's moves preserve history, while redirects have loop/double-redirect hazards; category redirects do not rewrite old membership references. These observations explain why article aliases alone cannot complete this migration. ([Moving pages](https://www.mediawiki.org/wiki/Help:Moving_a_page), [Redirects](https://www.mediawiki.org/wiki/Help:Redirects), [Category renaming](https://www.mediawiki.org/wiki/Help:Categories))

Reimport should match stable source/page keys and compare imported baseline, new upstream content and local revisions. This three-way conflict contract is a recommendation, not a MediaWiki import feature. Preserve source URLs/revisions, package version and required notices, and avoid overwriting local changes or recreating old global categories. Retaining attribution/history is useful, but does not by itself establish complete licensing compliance. The actual PF2e package's notices and source rights still need verification. ([Export and attribution](https://www.mediawiki.org/wiki/Help:Export), [Import collision cautions](https://www.mediawiki.org/wiki/Manual:Importing_XML_dumps))

Keep source books and version relationships independent from functional topics. AoN's source pages group a book's contents, while its Human page explicitly links the Legacy version. An old-name alias is different from a mechanically distinct version: neither matching titles nor a Remaster-first presentation justifies merging records. SharpMUSH must establish what alias/version information the import actually retains before promising comprehensive legacy lookup. ([Player Core](https://2e.aonprd.com/Sources.aspx?ID=216), [Human and Legacy link](https://2e.aonprd.com/Ancestries.aspx?ID=64))

Collection membership must never grant read access. Apply SharpMUSH requirements before exposing results, counts, labels, ancestors, previews or alias targets. A hidden-only collection must not disclose itself through navigation totals. MediaWiki itself cautions about partial read restrictions, so its organizational mechanisms are not an authorization template for private game material. ([Access-control limitations](https://www.mediawiki.org/wiki/Manual:Preventing_access))

## Conclusion

The next bounded deliverable should combine a genuine PF2e landing and preserved article/index journeys with the tested collection mechanics. Audit the existing category graph and parser metadata, define explicit landing/group records, and verify the four tasks above on the complete import alongside unrelated game pages. Keyboard/back-navigation, small-screen/zoom, protected-count and repeated-import/local-edit checks should form acceptance evidence. That turns “all pages remain reachable” into a test of whether readers can understand and use the reference.

Canonical qualification, aliases and richer rule facets deserve explicit subsequent milestones with migration and metadata costs recorded. Keeping those boundaries visible lets SharpMUSH improve exploration now without claiming that a filter, a renamed sidebar or a reference-site imitation has solved the whole problem.
