# Social account login and independent character credentials

Status: owner-approved full design for issue [#1983](https://github.com/SharpMUSH/SharpMUSH/issues/1983), approved for implementation on 2026-10-16. The owner additionally requires Grapevine Login as the fourth provider and preservation of all existing login methods. Migrated accounts retain their existing legacy fallback; it is never automatically disabled. Inspected main `14fd9ab7a` on 2026-10-16; application configuration tiles (#1984) are being integrated separately. Every choice labelled **Agent call** is proposed, not owner-approved.

## Intent, scope and authority

The owner confirmed the first providers are Discord, Google, Microsoft and Grapevine, and that one SharpMUSH account represents one person. That account can own many characters and link many external identities, including several from the same provider. An identity belongs to at most one account. Linking identities grants access to the whole account; it does not establish shared ownership or merge people. Account ownership is separate from a character's in-game controls and permissions.

Ship both native-client options: an independently managed persistent character password and an on-demand one-time character login secret. Neither requires setting an account password. Keep AccountSession as the only portal credential and preserve browser-terminal OTT and existing reconnect behavior. No ASP.NET Identity migration, new JWT bearer layer, bot integration dependency, email magic-link service, or automatic account merge is included.

Success: a newcomer signs in externally, chooses a username, creates a character, and connects in a native MU* client without creating an account password; existing players can explicitly link identities without losing their existing credentials or characters. Wrong-account linking, email collisions, recycled dbrefs, replay, revocation and race conditions must fail safely.

## Identity records and migration

Use a dedicated external-identity store and Mediator requests. Persist identity id, account id, stable provider registration id, validated issuer and subject, display label, creation/last-use time. Uniqueness is the full immutable `(registration, issuer, subject)` tuple, checked in the same Lightning write as attach/provision. Hash a canonical length-prefixed tuple for LMDB keys and compare stored full tuple after lookup. Display names, email and domains are never keys or authorization.

Google uses validated `iss` + `sub`; Microsoft uses tenant-specific validated `iss` + `sub`, retaining validated tid as metadata. Discord uses its API user id under a fixed Discord namespace after server-side token exchange and authenticated `/users/@me`. Changing provider client registration is an operator migration because subjects may be app-specific; never rewrite identity keys from emails. Failed identity authentication cannot provision a replacement for a disabled/deleted account.

**Agent call:** keep email null on social signup; provider email, if retained at all, is bounded display metadata and is never copied into unique account email, never marks IsVerified, and never links or recovers an account. User chooses a normal unique username on first signup. Same-email existing account is told to sign in to that account and explicitly link; no automatic merge or identity reassignment.

Make account PasswordHash nullable in model/store; null means no local account password. Migration preserves all nonempty hashes and all account/character links byte-for-byte. Historical empty hashes become null without turning unclaimed bootstrap accounts into social accounts. No bulk social provisioning. Use existing active/disabled/closed/deleted semantics; never treat absent password as disabled. Preserve MustChangePassword for existing records; newly social-only accounts start false. Existing forced password changes remain enforced until the required password is changed; adding social identity cannot bypass that flag.

**Agent call, compatibility boundary:** add explicit `AllowCharacterPasswordAccountLogin`. Migrate existing accounts to true to preserve legacy web/telnet account login; new accounts default false. Independent passwords and one-time secrets never enable it. Show existing users that their character passwords currently unlock the account; allow disabling legacy fallback after proving an explicit account method. Dedicated security proof never accepts the character-password fallback, even on legacy accounts. If an existing account only has character-password access, its authenticated session may enter an explicit one-time upgrade ceremony proving that same owned character password and installing an account method, with full account/session/status revalidation; audit this migration path and do not silently promote it into the regular reauthentication API. This preserves access without making character-password reset an implicit new account credential. Native secrets are rejected by all account/password/claim/security APIs.

## Server-owned provider flow

Use ASP.NET Core remote authentication handlers: OpenID Connect for Google/Microsoft and generic OAuth for Discord. Install only the framework-aligned package actually needed after design approval. No JS provider SDK or bearer ID token is trusted from the browser. A small provider adapter maps validated remote authentication to the immutable external identity; no hand-written JWT cryptography.

Use authorization code flow; OIDC uses PKCE S256, state, nonce, strict signature/issuer/audience/time validation and discovery over HTTPS. Discord uses confidential server-side code exchange, correlation state and its documented identify scope; enable PKCE only if supported by the live official provider contract, never assume OIDC support. Request minimal scopes: Google/Microsoft `openid profile` (no offline_access/Graph), Discord `identify` (no bot/guild/email scopes). Do not persist provider access/refresh tokens after obtaining identity. Denial, missing subject, wrong issuer, exchanged/replayed code, network error or missing configuration fails without account mutation.

**Agent call:** Microsoft initially supports personal and work/school accounts, with authority account type configured by operator. Common discovery is not itself a valid token issuer. Use supported Microsoft-aware issuer validation that validates concrete tenant issuer/tid and configured tenant allowlist; never disable issuer validation. Provider configuration must state which audience is registered. A single-tenant deployment can narrow this. All providers disabled by default.

Proposed endpoint contract:

- `GET /api/auth/external/providers`: enabled, ready provider identifiers/display names only.
- `POST /api/auth/external/{provider}/start`: login/signup purpose, relative allowed return path and remember choice; issues short-lived transaction and redirects to provider. Browser form requests get same-origin/antiforgery checks.
- `POST /api/account/external/{provider}/link-start`: authenticated explicit link, bound account/session, recent account proof, same-origin mutation protection; remote callback cannot choose another account.
- Dedicated handler callback paths `/signin-external-google`, `...-microsoft`, `...-discord`; callback validates and consumes server transaction once, checks current provider config generation and availability, then enters login/signup/link completion.
- `/auth/external/complete` portal page exchanges a one-use handoff via POST for the ordinary AccountLoginResponse; no AccountSession/provider/native token in URL or fragment. Bind handoff to transient Secure HttpOnly browser cookie and original transaction, expire after 60 seconds, consume atomically. Same-origin CSRF protection; no third-party redirect or cookie-only API auth.
- Unrecognized identity gets pending signup transaction (5 minutes) and username form. Explicit confirmation creates account+identity atomically, only if account registration/site creation gates permit. Cancellation leaves no account. Known identity logs in without signup gates, subject to normal login policy. No account or identity existence disclosure before provider proof.

Remote correlation/pending cookies are short-lived, Secure, HttpOnly and narrowly scoped, with SameSite chosen for the actual callback method (OIDC form_post requires None+Secure); clear on terminal outcome. Persist Data Protection keys as existing deployment requires. External cookies cannot authenticate APIs/hub. A return destination is an allowlisted local relative route and carries no credential. Before issuing the final account session, repeat active-account, registration/logins/sitelock checks with current requesting IP; linking must still have a live source session. Do not change the default AccountSession authentication scheme.

## Linking, recent proof and recovery

Security page lists local-password availability, passkeys, external identities with provider/label/last-use and explicit account-wide authority. Multiple identities of one provider are supported. A fresh proof of an existing method starts a five-minute server-held proof grant tied to account, current session and intended operation. Never rely on session sliding TTL or remembered-login restoration as recent proof. Accept dedicated account password verification, passkey assertion, or a new full provider authentication ceremony for an identity already attached to that account. Validate returned identity equality for reauthentication; a different identity cannot grant proof. Provider session selection/interaction is requested where supported; a completed remote ceremony proves current provider access, not a guarantee that the provider demanded a password.

Require proof for link-start, unlink, add/change/remove account password, email changes, passkey enrollment/removal, independent character password changes, and toggling legacy fallback. Link completion additionally proves the new identity through its own ceremony; check uniqueness transactionally. An identity already on another account returns conflict with no move. Duplicate same-account linking is idempotent. Credential list/removal count and mutations are transactional so concurrent unlinks cannot remove the final method.

**Agent call:** forbid removing the last configured usable account method (local hash, passkey, or identity on an enabled ready provider). Character passwords are not counted as a substitute for explicit account methods, even for legacy accounts. Operator disabling a provider can still strand users; admin tile shows affected accounts and requires explicit acknowledgement. Provider outage is not reliably detectable as permanently unusable; recommend adding a passkey, another provider, or optional local password after signup without forcing it.

Setting a first account password requires recent proof, new-password policy and confirmation, not a nonexistent old password. Changing an existing password requires its current dedicated password or recent proof through a different attached account method. Removing a password requires another remaining method. Passkey enrollment uses the same proof grant in place of CurrentPassword; passkey challenge remains bound/atomic. Email changes remain explicit account profile changes with proof; no automated email recovery is added.

Unlink, account-password removal/change, passkey removal and legacy fallback changes revoke all account sessions/remembered logins, outstanding proof/handoff/native secrets and drop account's live connections, then issue a replacement session only to the initiating browser if its remaining authentication is valid. UI warns before confirmation; other tabs must sign in again. Linking/addition does not terminate existing sessions. No provider operation changes character ownership or role grants.

Provider loss: sign in with another attached provider/passkey/local account password; existing character-password fallback remains only where explicitly retained. With no remaining method, contact staff. Staff uses audited password-reset authority and identity verification policy to establish a temporary local password and MustChangePassword; this revokes all sessions/secrets/connections. **Agent call, explicit security hardening:** keep players.moderate as the required recovery capability and add the same fresh role-priority target boundary already enforced by RoleManagementService.TargetAsync: a non-owner can recover only a different account whose highest held role is strictly below its own; it cannot recover the owner/God account or a reserved system account. The owner remains exempt from hierarchy, while normal self-service credential changes use recent proof rather than the staff-reset route. Require recent account proof from the staff actor. Target authority must be computed from persisted account/linked-character grants even for disabled accounts, rather than treating an inactive target as PermissionContext.None and therefore unprivileged. Recovery changes credentials, never enables a disabled/closed account. Existing reset currently has no such target guard; this is a new protection, not a preserved preexisting check. With no surviving owner credential, God recovery is an authenticated operator/console procedure, not an exception granting ordinary moderators control of God. No email-only recovery, no admin password viewing, no unauthenticated attach-by-email endpoint. Existing staff reset workflow is the deliberate privileged recovery escape hatch; document that authority, rather than invent recovery codes or claim email reset exists. Remote provider logout/revocation is not push-delivered automatically: it stops future provider ceremonies; already-issued SharpMUSH sessions remain until local expiry/revocation unless staff disables the account. Do not promise instant external-provider revocation detection.

## Owned characters and independent passwords

Existing portal creation can continue requiring an explicitly chosen independent character password. **Agent call:** additionally allow `Password: null` for a new socially authenticated owner's character; use a cryptographically random unguessable value hashed through the normal password service and discard it, not an empty hash. This is 'no user-set character password', not a network-reachable empty password. Keep account ownership and character creation policy, quota, home/start room and events. A failed ownership attach must roll back/reconcile creation before reporting success; never return a success with an unowned new character.

Expose `PUT /api/account/characters/{key}/password` with character creation timestamp, new password/confirmation and recent proof. Revalidate account active, exact current ownership, full DBRef and rate limits immediately at write. Dispatch existing `SetPlayerPasswordCommand` through Mediator; do not overwrite account password, legacy fallback flag, or other characters. An owner need not know a previous character password. Revoke outstanding native secrets for that character; offer explicit disconnect-other-clients action, while default password change does not kill already authenticated native clients (same persistent-password semantics as existing commands). Staff/game commands retain their current hierarchy and special #1 rules. Rechecking ownership must be serialized with ownership mutations at the provider write boundary.

Claiming an unowned legacy character still proves its existing persistent character password. One-time secrets cannot claim or transfer. Characters held by another account do not move because emails/providers match; use existing documented transfer/staff process. Owner-link changes revoke pending native secrets and proof grants; a recycled character key cannot inherit any credential. Never automatically import Discord bot identity links into either account auth or character ownership.

## Native one-time login secret contract

In Characters, select an owned character, choose 'Native client login', then 'Generate one-time login'. Show target, expiry countdown, copyable full command and revoke action. **Agent call:** use existing reserved login form `connect token nc1_<base64url-32-random-bytes>` (no character name or quoting); two-minute fixed TTL, no sliding. User pastes this in the native client's connect screen. Success enters only the bound character and normal login events; failure says 'Invalid or expired login token. Generate a new one in the portal.' Generate one independent credential per concurrent client. It cannot enter account-menu mode or call account APIs.

Use a separate `INativeLoginSecretStore`/service and purpose-prefixed parser dispatch so browser OTT remains `connect token <existing-ott>` and current 60-second issuance is unchanged. Share normal successful player-login completion and current bans/logins/sitelock checks; never route native secrets through persistent password verification or browser OTT lookup. Existing browser `mush-token` and switch-character response contracts and frontend transcript suppression remain intact. Browser token strings cannot redeem as native, native secrets cannot redeem as browser, session or remembered credentials.

`POST /api/account/characters/{key}/native-login-secrets` accepts full creation identity and authenticated live AccountSession. Mint requires current ownership, active account, no MustChangePassword, connect permission/site policy, and a proof no older than five minutes (using the same recent-proof service). No selected acting character is substituted for the requested owned character. Return plaintext once with opaque revocation id, full target DBRef and expiresAt; `Cache-Control: no-store`, no referrer, no credential in navigation URLs, ordinary roster, GET lists, audit or telemetry. GET status/list returns only revocation id/target/expiry; DELETE id only works for owning account. **Agent call:** 5 mints/minute/account, 10/minute/IP, maximum 10 outstanding/account; exceeding outstanding cap refuses rather than revoking someone else's pending client. Redeem limit: 10 failed attempts/minute/source IP and bounded per-connection attempts (existing throttles may be reused if equivalent); never attacker-lock an account by guessed token strings.

Store SHA-256 digest of 256-bit random secret, purpose/version, account id, full character DBRef (key+creation), minting session's non-secret internal identity or digest, issue/expiry time, revocation id and account/character credential epochs. Plaintext never persisted. **Agent call:** transient process-local store is sufficient for supported single-engine topology; restart invalidates all outstanding native secrets. Bound capacity and periodic expiry cleanup are mandatory. Atomic consume removes exactly once at `now >= expiresAt`; constant-time digest comparisons where needed. Build the store around an account credential gate shared by mint/redeem/revoke and account/ownership mutations; do not hold a lock across provider network calls.

Before bind, validate source session is still live and same account, exact character still belongs to that active account, account/character epochs still match, no forced password change and destination IP/hostname is allowed by current connect policy. Mint origin and native source may differ; do not bind to IP equality. Consumption and authorization form a serialized decision against local revocations/ownership changes. Final bind must pass that same credential gate or recheck a revocation epoch before committing; ban/ownership change winning first prevents login, and a change winning after bind uses normal live connection termination. A lost response consumes the secret; generate a replacement rather than retrying it. Revoking the minting session, account/global signout, credential removal, ban/disable, ownership change or explicit secret revocation invalidates pending secrets. No bearer token itself appears in indices/logs. Do not extend minting-session lifetime merely by checking native secret redemption; use a non-sliding live-session check.

Successful native login becomes a normal account-owned character connection; the secret is gone and has no authority over that session. Ordinary portal tab logout invalidates pending secrets minted there but does not retroactively disconnect native connections already established. Ban, account-wide signout/security removal and existing moderation can disconnect them. Provider unlink is account-wide security revocation as above. Existing WebSocket resume authorization is unchanged; a disconnected native client must use its persistent character password or a new secret, unless it uses the existing supported transport-resume protocol. Never implement a secret-replay grace period. Concurrent legitimate clients receive distinct secrets and do not evict one another.

Server cannot protect credentials pasted into a native client's own history/log; copy panel advises treating command as a password and prefers existing secure transport. Plain TCP telnet follows existing deployment transport policy; its contents can be observed in transit and TTL does not encrypt it. No promise of confidentiality on plain telnet. Operator deployment docs must state this explicitly. Server logging tests cover parser exceptions, NATS consumers, scheduler diagnostics, terminal transcript/command history, audit and HTTP body logging: capture no raw authentication command, secret, OAuth code or provider token. Existing length-only input logging is retained.

Use built-in server provider definitions, not installable plugins. Existing `/api/oauth/clients` and `OAuthAdm*` administration manages apps requesting SharpMUSH character access; provider settings must be distinct and clearly named "Sign-in providers". Existing authorized-app grants in account settings remain separate from linked sign-in identities. No existing remote-provider registry or callback pipeline was found to reuse; reuse AccountSession completion, provider-independent account operations and admin tile/secret primitives instead. Add one configuration tile each for Discord, Google and Microsoft under admin Applications using #1984's built-in configuration-tile contract after it merges. Tile owns enabled flag, client id, allowed public base URI, callback display, Microsoft audience/tenant restriction where applicable, readiness status and link to secret management. Tile configuration must have a real server reader, validation and admin authorization; do not register a public hosted app or user widget to implement authentication settings.

## Consequential proposed calls for owner review

These are choices to approve together with the full design, not extra implementation blockers after approval:

1. Preserve legacy character-password-to-account login only for migrated accounts via explicit flag; new social accounts default to character-only persistent-password authority, with an explicit upgrade path for legacy-only users.
2. Ship both native methods, allow new characters without a user-set persistent password using a discarded random hash, and use two-minute `connect token nc1_…` credentials requiring recent account proof.
3. Recovery without any surviving account method remains audited staff temporary-password reset; no email-only recovery or recovery-code product in this issue. Security credential removal/change signs out every account client.
4. Microsoft supports personal plus work/school accounts by default, operator-narrowable; provider registration changes initially require a controlled restart with explicit effective-status reporting.
5. Harden staff password recovery with the existing role-management target hierarchy and recent actor proof; ordinary moderators cannot reset equal/higher-privilege, owner, reserved or self accounts. This corrects a missing guard in the current reset endpoint.

All other exact endpoint names, type names, internal component split and UI placement are builder choices where they preserve these contracts; limits/TTLs above are explicit proposed defaults. No change grants shared account ownership, email linking, external token API authorization, or automatic migration of bot links.

## Primary protocol references

- [ASP.NET Core OIDC web authentication](https://learn.microsoft.com/aspnet/core/security/authentication/configure-oidc-web-authentication): framework confidential code-flow/PKCE integration; reuse handlers rather than writing token validation.
- [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect): use stable subject/issuer and validate token; email is not the account key.
- [Microsoft ID token claims](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference) and [Microsoft token issuer boundaries](https://learn.microsoft.com/en-us/entra/identity-platform/access-tokens): tenant-aware issuer/subject identity and validation.

## Approved Grapevine addition

Grapevine uses OAuth2 authorization code with the `profile` scope, authorization endpoint `https://grapevine.haus/oauth/authorize`, token endpoint `https://grapevine.haus/oauth/token`, and authenticated user endpoint `https://grapevine.haus/users/me`. Use the returned stable `uid` under issuer namespace `https://grapevine.haus`, scoped to the configured registration; username/email are display metadata only. Follow [official Grapevine Login documentation](https://grapevine.haus/docs). Do not assume OIDC, PKCE, or unsupported client authentication; verify capabilities against official source before configuring the adapter. Add its dedicated provider tile, secret `auth.grapevine.clientsecret`, and the same readiness, generation, linking and acceptance coverage as the other providers.
