# Native semantic wiki architecture and validation design

**Status:** Architecture and isolated prototype approved by the user on 2026-10-17. Production release and deployment are not authorized. Numeric limits below remain unvalidated prototype hypotheses, not measured guarantees. Original design date: 2026-10-16, America/Chicago.

**Intent:** Make relationships such as class→feats and ancestry→heritages navigable, and support a few trustworthy generated lists, while protecting game responsiveness and private wiki content. Store typed facts and use indexed, bounded lookups. Do not assume a graph database or expose unrestricted graph traversal.

**Approved choices:** Staff property editor plus package manifest fields; same-collection facts initially; optional exact counts; explicit restart and capacity responses; the documented residual activity/timing channels. Implementation proceeds through the phase gates below. Target hardware and numeric performance acceptance remain measurement decisions, not established guarantees.

## 1. Evidence and current contracts

This design builds on [the committed organization research](../../research/pf2e-wiki-organization.md), [the semantic research update on #1970](https://github.com/SharpMUSH/SharpMUSH/issues/1970), and [the architecture requirements](https://github.com/SharpMUSH/SharpMUSH/issues/1970#issuecomment-6229283551). The semantic-linking report, metadata inventory and native-source fit working notes are retained locally as supporting research; the proposal below states the relevant findings and links the pinned source. Code inspected at `dd8226a88d0416fdd03d442dcd2afa32a196ff63`, merged as `b52ffb91ffd168b96365270a5afc28ab8acfd7a7`.

The pinned PF2e pack has 4,711 pages, 130 categories and 22,312 resolving wikilinks. Its four-root category forest and authored hubs should remain. It has **no typed per-page gameplay fields** in its manifest. Markdown retains levels on 3,396 entries, spell-family ranks on 659, traditions on 408, and source footers on all 4,580 Main articles. Extraction is a reviewed content migration, not a runtime graph parser or a claim of complete rules data. See [pinned package](https://github.com/SharpMUSH/SharpMUSH.Packages/tree/2659a733a4519b76e64a727be2687794afc04f6b/pf2e-remaster).

The binding [engine data trunk](../../design/engine-data-trunk.md) requires data requests with explicit cache policy, handlers over aggregate stores, providers without Mediator/cache, and startup migration before readers. It explicitly documents the existing `WikiStoreService`/`IWikiStore` seam. Relevant observed contracts:

| Existing component | Observed behavior and implication |
| --- | --- |
| `IWikiStore`, `WikiStoreService` | Normalize/render before persistence; current wiki methods mostly call the store directly and lack cancellation tokens. New bounded semantic operations need explicit request/token/work-budget contracts. Do not assume the existing methods already provide them. |
| `LightningDatabase.Wiki.cs` | Local page IDs differ from game dbrefs. Namespace/slug uniqueness remains global. Page/list-index writes share one write job. Listings/counts can scan index entries and decode bodies for restrictions; they are not a safe semantic-query executor to reuse unchanged. |
| `WikiAccessService`, `WikiVisibility` | Grants compile namespace/category/page restrictions; visibility is applied before pagination/counting. Own drafts, staff access and package membership matter. |
| `WikiLocalizationService` | IDs/source locale are stable; translation revision/publication is separate. Current localization loops per page; semantic listings require compact batch projection. |
| `PackageWikiContent`, planner/service | Baseline/live/new merge covers body, title, metadata and requirements. Properties are absent. Applying a package currently uses several reversible mutations; it is not one atomic transaction for the whole import. |
| `LightningStore`, `LightningWriter` | Reads synchronously enter a short storage read section; writes serialize, can run inline when uncontended, and otherwise join the writer queue. A task's async signature does not isolate its synchronous work. |

SMW independently warns about query size/depth and nested query-driven formatting. Those lessons support explicit limits; its syntax/defaults are not a SharpMUSH contract. [Query restrictions](https://www.semantic-mediawiki.org/wiki/Help:Query_restrictions), [Performance guidance](https://www.semantic-mediawiki.org/wiki/Speeding_up_Semantic_MediaWiki), accessed 2026-10-16.

## 2. Recommended scope and alternatives

**Recommend native authoritative facts, transactional forward/reverse indexes, and one-hop structured queries.** First ship inverse panels; then a small generated-list vocabulary. Ordinary backlinks are a separately labelled “mentions” relation derived from the Markdown AST, never evidence of prerequisites or class membership. Preserve original prerequisite prose. General Boolean prerequisite evaluation, arbitrary joins, inference, subproperty expansion, regex/full-text filters, path search and user-programmable result templates are separate reviews.

| Alternative | Benefit | Cost / decision |
| --- | --- | --- |
| Scan Markdown or page rows per request | Minimal persistent schema | Cost grows with all content, extraction repeats, permissions/projections amplify work. Reject for semantic reads. |
| Native facts + indexes in current provider | Atomic writes, existing backup/deployment, no extra service | Shares writer, CPU, memory and disk; strict budgets and measured interference are mandatory. Recommended prototype. |
| External asynchronous search/read model | Stronger resource isolation, specialized search later | Durable outbox, version lag, ACL revocation fences, reconciliation and another operational dependency. Reconsider if native isolation fails measurements. |
| Graph database / unrestricted query language | Broader traversal expressiveness | Does not remove high-degree expansion or ACL cost; creates migration and operational scope before a need is established. Do not select initially. |
| Precomputed named lists | Predictable popular views | Must remain current, bounded and authorized at read time. Add selectively after measuring repeated queries; not a universal cache. |

A same-collection prototype is recommended; cross-collection relations require an explicit later scope/identity policy. Existing global canonical-name collisions remain part of #1970's identity milestone. Opaque local IDs prevent accidental retargeting but do not themselves create independent collection-qualified URLs.

## 3. Authoritative data and identity

Proposed new records, separate from page Markdown:

- **Property definition:** stable qualified key (`pf2e:class`), local internal property ID, schema version, localized labels, datatype, single/multiple cardinality, allowed target kinds, normalization and index declaration. Freeze definitions once used; incompatible changes require migration.
- **Fact set:** subject page ID, property ID, typed value, provenance, fact-set version. Start with PageRef, signed integer, Boolean and registered enum/short keyword equality. No locale-dependent number parsing, decimal/range semantics by accident, or unrestricted string indexing.
- **PageRef:** opaque local page identity plus retained portable source key. A deleted/recreated page never inherits incoming relationships merely because its title/slug matches.
- **Portable key:** `(package ID, namespace, explicit source entry key)`. For the old pack, record the initial namespace/slug mapping as a migration baseline; do not guess identity through future renames. Aliases are explicit mappings, not equality-by-title or Remaster/Legacy merging.
- **Provenance:** package/version, source entry/revision when retained, extraction rule/version, and local edit/override state. Distinguish source-book citation from importer provenance. Unknown is distinct from zero/false/not-applicable.
- **State versions:** introduce a monotonic page state version covering facts, metadata and ACL-relevant changes. Current source `RevisionNumber` is insufficient: title/metadata changes do not always append body revisions. Maintain semantic commit sequence, index generation/schema version, requirements epoch, visibility-partition epochs and page/translation summary versions.

Recommend declared package fields plus a structured staff editor as authoritative authoring. Convert systematic Markdown offline with a coverage/error report; never infer facts from prose on a request. Tradition can initially be a registered enum with an optional existing landing-page link; do not manufacture empty articles to make every literal a PageRef. Source publication details and compound prerequisites need grouped assertions later: separate book/page arrays lose pairing, and flat `requires` edges lose AND/OR/threshold meaning. SMW's [typed properties](https://www.semantic-mediawiki.org/wiki/Help:Properties_and_types), [inverse properties](https://www.semantic-mediawiki.org/wiki/Help:Inverse_properties), [subobjects](https://www.semantic-mediawiki.org/wiki/Help:Adding_subobjects) and [Reference datatype](https://www.semantic-mediawiki.org/wiki/Help:Type_Reference) establish useful prior art, not syntax compatibility.

## 4. Store and request boundaries

Proposed responsibilities, not implemented APIs:

| Unit / intended file family | Responsibility |
| --- | --- |
| `Contracts/Models/Wiki/Semantics/*` | Versioned property/value/query/result DTOs; no database or parser expressions. |
| `Library/Models/Wiki/Semantics/*` | Canonical facts, query/work limits, immutable authorization stamp and compact summaries. |
| `Library/Stores/IWikiSemanticStore.cs` | Transactional page/fact mutation and bounded candidate/projection batches. Provider-specific cursor bytes never escape storage as readable public data. |
| `Library/Queries/Database/Wiki/*`, `Commands/Database/Wiki/*` | Data requests such as semantic slice reads and normalized page/fact commits; uncached initially. No request that merely locates/calls a service. |
| `Implementation/Handlers/Database/Wiki/*` | Store orchestration; no handler-owned FusionCache. |
| `Library/Services/WikiSemanticQueryService.cs` | Admission, validation, planning, work accounting, visibility and response fencing. Never runs on the game's immediate queue. |
| `Database.Lightning/LightningDatabase.WikiSemantics*` | Keys, bounded reads, atomic replacement, epochs, journal and rebuild generations. No Mediator, cache, rendering or permission-service calls inside transactions. |
| Server endpoint / client generated-block components | Authenticated reader context, cancellation, batched hydration, explicit incomplete/error states. |

The new semantic aggregate must use data requests consistently. Closing the legacy write seam is real work: audit every semantic-affecting `IWikiService` mutation, package apply/undo/uninstall, revision restore and requirements write. Normalization/rendering stays above storage as pure preparation; handlers persist normalized data. Refactor the wiki facade/request boundary under architecture review instead of silently mixing direct writes with Mediator-cached reads. Do not migrate unrelated engine aggregates. Keep semantic request caching off until this coverage is proved; uncached requests are the trunk's default, not an omission.

Proposed physical indexes use fixed internal IDs; external property keys and text values live in registries rather than creating unbounded LMDB composite keys:

| Index | Key sketch / use |
| --- | --- |
| Canonical fact | `(subject, property, canonical value)`; exact per-subject membership/projection |
| Forward relation | `(subject, property, target)`; capped related targets |
| Reverse / equality posting | `(collection, source visibility class, property, typed value/target, subject)`; direct inverse and selective equality |
| Integer posting | Same prefix, then sortable signed integer, then subject; declared ranges only |
| Compact page/label summary | ID, state version, namespace/category IDs, publication/author, title/fallback metadata; no bodies |
| Internal posting statistics | Per indexed prefix; planner hints only, never reader-visible estimates |

Every record inspected, duplicate skipped, membership probe, registry lookup and summary byte counts against a work budget. Sortable integer encoding must be tested across negative/zero/positive boundaries. Initially, ordering properties must be single-valued. Every supported order is a total order ending in immutable subject ID, and each subject occupies exactly one position across cursor pages. Reject ordering by multivalue properties. Multivalue equality/range predicates use explicitly existential semantics and must stream unique subject candidates; page-local deduplication alone is insufficient. Page counts deduplicate subjects; relation counts cannot accidentally count edges as pages. Do not create property×sort×facet indexes speculatively; an unsupported sort requires a new measured index or bounded materialization plan.

## 5. Permissions precede observable membership

Build a server-side reader snapshot through existing grant resolution and wiki requirements, not client-supplied permission filters. The stamp includes bound account/character identity, grant/role-policy version, requirements version and collection membership version. Add trustworthy versions where existing APIs lack them. Recheck before emitting results; if relevant authorization changes, discard the response. A revocation after response bytes have been sent cannot retract them; document the final authorization check as the response's authorization point.

Both ends of every relation must be readable, including draft rules. Authorize supplied target predicates before using them; missing and unreadable targets share the existing nondisclosing outcome. Hidden labels, unknown-property diagnostics, source citations, facet options, existence flags and result snippets require the same policy. Sensitive facts on public pages are not automatically property-private; initially require facts to share their subject's visibility, and do not model secret values on a public subject.

**Recommended prototype: visibility-aware source posting partitions.** A class identifies structural namespace/category requirements, explicit page-rule set, publication state and draft author. A catalog compiles classes against the current requirement snapshot; changing namespace/category requirements changes that compilation, not every incoming edge. A page's class change moves its own bounded outgoing postings atomically. Ordinary property queries seek only admitted classes; a high-degree hidden bucket must not consume the visible query's edge budget. Forward target checks remain batched because outgoing facts are bounded. Collection/page metadata and final visibility checks remain authoritative even when class membership is indexed.

This is additional architecture, not an existing feature. Catalog compilation has its own limit; excessive distinct classes are a declared authoring/index-capacity error rather than an unbounded query-time permission scan. Prototype the class count and exact draft/bypass semantics before fixing production quotas. Maintain the catalog only for semantic subjects, reclaim unused classes, and verify that class sharing never weakens category/page requirements. If partitions cannot preserve visibility or explode under realistic ACL diversity, keep the feature gated and compare another read model; do not substitute privileged results plus browser filtering.

There is no claim of constant-time, cryptographically oblivious graph access. Shared-resource timing and operational saturation remain side channels. Rows, labels, exact counts and facets must enforce content visibility. However, admitted-source epochs can expose otherwise invisible activity through a cursor restart: changing an unreadable-target relation on a readable source still changes that source partition. Collection maintenance gating also exposes operational activity. Accepting this residual invalidation channel requires an explicit prototype threat-model decision before implementation; stronger noninterference needs a separately reviewed dependency/version scheme. Test result visibility and these residual channels explicitly, including budget boundaries. Budget/error messages expose no raw examined counts, hidden degree, planner selectivity or unfiltered estimates. Strict timing noninterference would require a separate threat-model decision, not a larger timeout.

## 6. Bounded one-hop planning and pagination

Initial grammar: one explicit collection, conjunctions of registered property equality and integer ranges, a directly supplied visible relation target, requested scalar columns, an allowed indexed order, and a keyset cursor. No NOT, arbitrary OR, wildcard scan, property chain, recursive category expansion or implicit subproperty reasoning. A PageRef lookup is one hop; projecting a related label does not authorize following that page's relationships. Reject unsupported conditions in full; never silently drop them.

Planner sequence: validate size/types; authorize predicates and compile allowed classes; select an indexed driving prefix; stream candidates in supported order; test remaining predicates with bounded point probes; batch source/target visibility and label projections; find an additional **authorized** row if claiming a next page; fence data/auth versions; serialize within response limits. Do not load entire posting lists to compute their intersections or sort all matches for a 50-row page. A selective prefix is a performance aid, not permission to exceed runtime budgets if statistics are stale.

Return an explicit result union: complete page, refine-required/work-limit, data-changed/restart, index-unavailable, invalid query, or busy. A valid complete page carries rows and a continuation only when justified. Do not return a partial page as exhaustive or equate a budget stop with zero matches. Server diagnostics retain exact work counters; public responses do not. Request-specific data-change retry, if used, consumes the original deadline and counters and is limited to one attempt.

Cursors are authenticated **and opaque**, binding normalized query, reader scope, schema/index generation, an authorized-partition version digest, predicate-target versions, authorization stamp, order position, locale and expiry. Never put hidden keys or raw scan counts in readable signed tokens; fix/pad token shape so its size does not reveal denied partitions. No LMDB transaction survives between pages. Reject stale cursors and restart; no offset scans. **Avoid an all-content collection epoch for ordinary fact edits:** compute the bounded digest from admitted source partitions, reducing invalidation from unreadable sources. This does not guarantee hidden-edge noninterference on readable sources; section 5 documents that residual channel. Changes confined to a denied source partition do not change the admitted-partition digest. A source's class move bumps its old/new partition versions atomically. Relevant visible edits can still force restarts; measure this tradeoff.

A high-degree inverse list remains a paged indexed range, not a materialized neighbor set. Its count is a different operation. Multiple hops multiply intermediate cardinalities even when the final limit is tiny; they require separate grammar, work accounting and architecture approval. Cycles are harmless only because the initial executor never traverses them.

## 7. Counts, facets and rendering receive separate budgets

Default requests do not compute totals or facets. Optional exact count/facet operations reuse visibility-aware planning under their own admission and work limits. Return `Exact(n)` only after complete authorized evaluation; otherwise `Unavailable` with no partial total or global estimate. Registered low-cardinality enums are the first eligible facets; cap distinct buckets. Never count an unreadable source or disclose an unreadable PageRef value. Fast per-prefix sums are allowed only when their scope/ACL/target-validity semantics exactly match the requested query.

A named popular view can precompute candidate IDs/order under a versioned query definition. It still needs current authorization and target liveness; its private membership and aggregate counts are not shared reader answers. Updates to an entry must not synchronously rerender every hub that refers to it.

Generated blocks hydrate at view time, outside cached shared article HTML. Batch duplicate query signatures across the article, run no queries inside result rows/templates, and project compact titles/scalars without fetching target bodies. One page render shares a parent budget across all blocks; nested generated blocks and recursive transclusion are prohibited initially. The existing `WikiLocalizationService.LocalizeAllAsync` per-page loop must not become a semantic N+1 path: add bounded bulk translation-summary/title reads, preserve fallback/draft visibility, then create localized routes. Canonical facts stay source-locale independent; translating prose cannot edit them. Per-translation mention backlinks, if later added, remain a distinct index.

## 8. Transactional coherence, fan-out and recovery

Canonical fact replacement, compact subject metadata, own forward/reverse/index deltas, state version, affected visibility-partition versions and semantic commit sequence must commit in **one provider job**. Validate/render outside that transaction; compare expected state version inside it. Failed validation or write conflict leaves all unchanged. Synchronous indexes avoid a period where accepted facts and direct inverse panels disagree. Cap outgoing facts/serialized payload so a single edit cannot hold the writer for an unbounded degree expansion.

Deleting a popular target must not synchronously rewrite every incoming subject. Tombstone/remove its liveness metadata atomically and remove only its own bounded outgoing facts. Reads refuse that target and hide broken relation values; retained incoming facts continue to name the original ID and can be repaired/garbage-collected in bounded maintenance batches. A same-slug replacement never inherits them. Property-definition removal similarly disables use first; physical cleanup is batched. ACL changes fence readers by version and do not fan out through a target's incoming edges. Every page that can be a relation target must update its compact state/liveness/publication summary on relevant writes, including pages with no outgoing semantic facts; publishing such a target must remain observable to final query validation.

Package fields must join baseline/live/new comparison, preview, conflict decisions and undo. Recommend property-level three-way comparison, with a multivalue property treated as one conflict unit initially: do not silently union upstream removals with local additions. The selected live body and facts are authoritative; retain the new upstream baseline separately. Apply each page/fact/baseline ownership change atomically where the provider can do so, via an explicit bounded aggregate commit. The complete 4,711-page installation is **not** one writer transaction. Preserve the existing package operation/compensation semantics; block semantic reads for an applying/recovering collection until it reaches a coherent operation checkpoint. Do not advertise package-wide snapshot isolation that the installer lacks.

Secondary rebuilds use a new generation. Before scanning, start a durable bounded after-image journal in the same job as every relevant mutation. Read canonical subjects in short ID batches, recording versions; replay journal changes in sequence, with idempotent checkpoints and deletion markers. Each after-image is bounded by the fact-set quota. Before flipping the generation, use a short writer job to verify no unconsumed sequence and atomically change the active-generation pointer. If writes outrun replay, yield/back off or abort the rebuild; do not hold the writer until it catches up. Journal retention exhaustion aborts the new build, never drops active writes. Validate counts/checksums against a slow reference evaluator before publication. Clean retired generations incrementally after active request leases expire; cursors for old generations restart.

Schema meaning changes are different from rebuilding the same index: stage a reviewed canonical-fact migration with conflicts/invalid-value reporting. Do not reinterpret live data under a new type while an old generation answers queries. Initial property definitions can be additive and immutable, avoiding that migration in the first slice.

| Failure | Required outcome |
| --- | --- |
| Cancellation before admission | No work or writes; release admission ticket. |
| Cancellation after write admission/commit | Commit status can be uncertain to caller; use mutation ID/expected version and status lookup. Observe actual completion; do not free a still-running slot or retry blindly. |
| Crash during page mutation | Transaction commits all related records or none; validate active schema/generation on restart. |
| Crash during rebuild | Resume from durable checkpoint/journal, or discard incomplete generation; active generation remains authoritative. |
| Missing/corrupt active projection | Mark semantic queries unavailable; ordinary page reading remains possible. Repair/rebuild under a bounded job; never answer empty success or scan all Markdown as fallback. |
| Import/undo interruption | Report applying/recovering state, finish compensation/reconciliation, then reopen semantic reads. No automatic destructive reset. |
| Storage full / map limit | Abort bounded mutation, retain canonical/active state, report capacity error. Rebuild requires preflight space allowance for both generations and journal. |

## 9. Isolation, backpressure and caches

Use a dedicated bounded wiki-query admission queue and a small worker set. Admission happens before enumerating facts or retaining large request state. Account/principal and global caps apply to every caller, including admins; rebuild work has a separate single low-priority admission. Do not enqueue graph work into the immediate game-command queue or launch unbounded `Task.Run` calls. If dedicated workers perform synchronous `Store.Read` calls, their thread count is fixed. This limits concurrency, not physical CPU/disk contention; measured interference remains a release gate.

Read batches copy bounded keys/summaries then dispose/reset the transaction **before** async grants, rendering, networking or waiting. Fence batches with the same authorized-partition digest and predicate-target versions. Track versions for every source, target and translation whose state influences membership, projection, lookahead, counts or facets, including targets excluded for liveness, publication or permission. Charge this dependency set and its deduplication against the original budget. Perform a bounded coherent final validation of all observed dependencies and authorization, using one metadata read snapshot or an equivalently proved stable-version protocol. Checking returned targets alone is insufficient. If validation cannot fit its budget, return work-limit; on relevant changes return data-changed rather than an exact answer from mixed snapshots. Target liveness/ACL/label checks use point/batch reads, avoiding an incoming-edge invalidation walk. Charge digest construction and final validation to the same budget. No reader retained across pagination, queued work or response streaming. LMDB's own documentation states that reads retain a snapshot, long-lived readers prevent reuse of freed pages, and there is only one write transaction; readers do not directly lock out the writer. [LMDB introduction](https://raw.githubusercontent.com/LMDB/lmdb/mdb.master/libraries/liblmdb/intro.doc), [LMDB API caveats](https://raw.githubusercontent.com/LMDB/lmdb/mdb.master/libraries/liblmdb/lmdb.h), accessed 2026-10-16.

Only one maintenance write batch may be outstanding. Prepare extraction outside the writer, submit a bounded batch, await completion, yield and check cancellation/game pressure before another. Never fill the existing 10,000-job writer channel with rebuild work or globally pause/reconfigure the writer for semantic queries. Add admission/queue-wait telemetry before choosing an overload circuit breaker. A synchronous native read cannot promise immediate cancellation during an OS page fault: keep its worker/lease occupied until it actually exits, and reject new work rather than spawning replacement workers. Cancellation checks inside loops are mandatory; cancellation cleanup must not abandon committed state.

Query-result caching is **off for the first performance gate**. Internal immutable schema/visibility-class compilations can use bounded, version-keyed caches, and must pass cold paths. If later caching raw candidates, reapply authorization and liveness at read time. Caching reader answers requires reader/grants, requirements, admitted-partition digest, predicate-target versions, schema/generation, locale and every observed source/target/translation dependency version, including exclusions, in the key; prohibit stale/fail-safe private results. No handler/provider owns FusionCache. Durable epochs protect against crashes after commit but before process invalidation; current Mediator invalidation still runs before/after writes, including failure paths. Update the subject's affected partition versions and summary version in bounded work rather than maintaining a hub dependency graph. A global requirements/schema policy change can fence all queries, while the coarse admitted-source version scheme retains the residual invalidation channel described in section 5; it does not guarantee that every invisible edge or excluded-target edit leaves reader-visible restart/cache behavior unchanged. Keep detailed sequences internal and measure restart/cache-churn cost.

## 10. Proposed initial budgets — all unvalidated

These numbers are experiment settings, not defaults to ship. Service limits apply before provider reads; provider loops enforce work limits even when called directly by tests. Never let cache hits exempt the request or its generated blocks from admission/response limits. No admin “unlimited” bypass.

| Dimension | Starting hypothesis | Measurement / failure behavior |
| --- | --- | --- |
| Query shape | One collection, ≤4 conjuncts, one hop, ≤6 scalar columns | Reject unsupported AST before work; test all limit±1 cases. |
| Results | 25 default, 100 maximum; ≤256 KiB serialized | Cap field/value previews; no body projection. |
| Work | ≤2,048 distinct subjects, ≤8,192 visited postings/point probes combined, ≤2 MiB decoded/copied data, ≤4 MiB managed working buffers | Charge before access/allocation, including duplicates and failed predicates; refine-required, not partial success. |
| Authorization preparation | ≤1,024 semantic visibility classes/collection, ≤65,536 scope checks and ≤1 MiB catalog metadata | Explicit semantic-authoring capacity rejection; measure ACL diversity and class reclamation before adopting quota. |
| Read batch | ≤128 records or 128 KiB; check cancellation every ≤32 steps; 5 ms transaction-duration target | Size/operation bounds are enforceable; duration is telemetry/SLO, not guaranteed preemption of native I/O. |
| Query execution | 200 ms wall deadline plus ≤50 ms queue wait | Busy/refine-required; queue and retries share overall request budget. |
| Counts/facets | Explicit request, ≤4,096 subjects /16,384 probes /4 MiB, ≤16 enum buckets, 200 ms; one active aggregate | Unknown when incomplete; no approximate hidden counts. |
| Whole article | ≤3 generated queries, shared ≤4,096 subjects /16,384 probes /4 MiB, 300 ms | Deduplicate; no nested queries; errors visible per block without restarting full rendering. |
| Admission | 2 active queries globally; 1 active and ≤2 queued/principal; ≤16 queued globally | Reject excess before storage; include aggregate work in the global cap. |
| Facts | ≤128 values/subject, ≤32/property, ≤64 KiB canonical facts, ≤256 UTF-8 bytes/keyword | Reject over-quota edit/import before mutation. Registry IDs keep index keys bounded. |
| Rebuild | 1 worker, ≤32 subjects /256 KiB prepared delta per write job, 1 outstanding job, 5 ms writer-hold target | Reduce batches/pause if writer latency rises; one oversized subject is a clear validation error, not a larger batch. |
| Rebuild journal | ≤64 MiB or configured space allowance; preflight active+new index+journal | Abort staging generation on exhaustion; keep active data available. |

Prototype latency hypotheses on agreed hardware: cold process p95 ≤100 ms/p99 ≤200 ms for accepted direct/equality queries on the real pack; warm p95 ≤50 ms/p99 ≤100 ms. Storage-cold results are reported separately, never relabelled process-cold. Compare game commands under fixed load with baseline: proposed acceptable added p95 ≤max(5 ms, 10% of baseline) and p99 ≤max(10 ms, 15%). These are review candidates. Safety failures, leaked data, unbounded writer/read holds and incorrect results fail regardless of average speed.

## 11. Phased prototype and acceptance plan

This is a review/validation plan, **not an executable implementation plan**. After architecture approval, write the file-level TDD plan with the approved numbers and interfaces. Each phase is independently rejectable; do not continue to generalized search simply because direct lookups pass.

**Phase A — lock contracts and datasets.** Define property ownership, authoring syntax, version stamps and the visibility-class model. Map every create/edit/title/category/requirements/translation/restore/package/undo/delete path to its transaction and invalidation responsibility. Build fixtures from the pinned 4,711-page pack, retaining its license links and authored hubs; record extraction rules, coverage, rejects and unknowns. Select small class/ancestry/level/rank/tradition examples verified against authored entries. Deliver a schema/dry-run report, a path-coverage matrix and a slow authorized reference evaluator. Tests should include ambiguous source IDs, literal normalization, duplicate facts, deleted/recreated targets and local source-key migration.

**Phase B — atomic facts and one-hop projection.** Prove per-page commit invariants, reverse/forward symmetry, read-budget accounting and crash/cancellation outcomes. Tests include `MutationIsAtomicAcrossFactsAndIndexes`, `MetadataOnlyEditMovesStateVersion`, `DeletedTargetDoesNotRetargetReplacement`, `DeniedSubjectsDoNotConsumeVisiblePostingBudget`, `GrantRevocationDiscardsPreparedResponse`, and `ClassCatalogLimitDoesNotCreatePartialFacts`. Reproduce import keep-mine/take-theirs/undo and property removals with real installer planning. Measure uncached direct panels before any query-result cache exists. Stop for architecture review if ACL partition cost or writer interference fails.

**Phase C — limited generated lists and aggregates.** Add only indexed equality/range conjunctions and supported sort orders. Compare every result/count against the reference evaluator with randomized small graphs and the real pack. Tests include duplicate-subject deduplication, stale statistics, high-degree streaming, no-offset cursor work, epoch change between batches, hidden-only mutations, partial ACL selectivity, unsupported negation/chain rejection, and `BudgetStopIsNotEmptyOrExactCount`. Verify batched localization and `GeneratedRowsNeverExecuteQueries`; instrument store calls to prove no per-row reads of target bodies and no query-per-template. Keep “Alchemist feats by level” and ancestry/heritage return journeys intact in portal and eventual in-game output.

**Phase D — recovery and load gate.** Kill the prototype at page commit, journal checkpoint, replay, generation flip, import compensation and post-commit/pre-invalidation boundaries. Reopen and compare canonical facts/indexes/query outputs; no lost local override, stale private result or silent fallback. Measure index overhead, page faults, peak working set, allocated bytes, read duration/reader slots, writer wait/hold, queue age/rejections, cancellation tail, rebuild lag/throughput and game command p95/p99. Do not approve Phase E without recorded results and revised limits.

**Phase E — a separate decision.** Consider selected materialized views, cross-collection facts, more sorts or facets only when evidence shows a reader task needs them. Multi-hop, requirement evaluation, free-form semantic templates, external read models and graph databases each require a new cost/privacy model and approval.

## 12. Measurement matrix and release decision

Use the actual package plus deterministic generated data at 10× and 100× page count (47,110 and 471,100), with varied fact counts. Include one target with hundreds of thousands of incoming edges, maximum outgoing facts, rare intersection predicates over common postings, 99.9% denied candidates, many ACL classes/draft authors, zero results, cycles, duplicate paths, hot property changes, long keywords and malformed quotas. Oversized graphs must be rejected/bounded predictably; passing every query is not the goal. Tests must also mutate hidden-only graphs while holding the authorized graph constant and compare public payloads/counts/cursor claims.

Run mixed query/edit/import/rebuild workloads beside a repeatable game workload with the same host/provider and sync mode as baseline. Keep command mix, offered rate, concurrent sessions, CPU/memory quotas, disk and dataset seed fixed. Measure query arrivals at 1, 2, 8 and 32 concurrent callers to verify admission/backpressure rather than merely peak throughput. Tune command load to a representative non-saturated baseline, then repeat near saturation. Do not improve query numbers by silently dropping game commands or moving their work outside the timing window.

Report query signature, index path, candidates/probes/bytes charged, ACL preparation, projection/formatting, queue and storage timings separately. Use at least 10,000 warm requests per important query shape across several runs for tail distributions, 20 fresh-process starts for process-cold behavior, and isolated disposable VM/container experiments for true cold storage. Do not drop production host caches. Cache-off tests are the primary safety gate; warm-cache results describe optional acceleration. Profile allocations and retained memory separately; memory-mapped address-space reservation is not resident memory.

Index/rebuild space is measured as actual used/allocated storage and duplicate generation peak, not only logical serialized fact bytes. Check long-lived-reader indicators during concurrent updates. Define an observed interference threshold that automatically stops new maintenance admissions; do not invent a fixed scheduling guarantee from the shared writer's current FIFO behavior. Record unsupported cases, gate failures and mitigations. Architecture approval for a prototype is not release approval for a feature that misses these bounds.

## 13. Decisions to review and remaining user choices

Recommended architecture decisions: native fact registry; explicit declarations rather than request-time extraction; ID-based one-hop indexes; canonical facts and direct indexes committed together; visibility-aware source partitions plus endpoint rechecks; no query-result cache initially; bounded dedicated query admission; short reader sections; bounded partition-version invalidation; staged/journaled rebuilds; no nested query rendering; original prerequisite prose retained.

The user approved the recommended authoring experience (staff property editor plus manifest fields), same-collection facts initially, optional counts, and opaque restarts and explicit capacity errors on 2026-10-17. Agree target deployment hardware and acceptable game-latency impact before treating numeric SLOs as acceptance criteria. Any requirement for property-level secrets or strict timing noninterference changes the design and needs its own approval.

Builder-review questions: Can every legacy write path maintain the epochs/indexes? Can a target/category ACL change avoid degree-sized rewrites? Can an authorized high-degree query progress without scanning denied partitions? Can source/category/page requirements and own drafts share classes without weakening rules? Does every rejected/empty/count/cursor state avoid content disclosure? Can rebuild catch-up fail safely under continuous writes? The prototype must answer these with measured/tested evidence, not a cache hit or a small happy-path demo.

## Independent review checkpoint

A fresh architecture review identified and corrected three gaps: multivalue ordering could repeat subjects across cursor pages; admitted-source epochs do not provide complete hidden-edge invalidation noninterference; and final consistency checks must include observed-but-excluded targets, not only returned rows. These corrections narrow the proposal and add explicit measurement/threat-model requirements. User approval on 2026-10-17 permits an isolated prototype, subject to the phase gates; implementation and measurements are tracked separately.
