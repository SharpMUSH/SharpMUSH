# Changelog

SharpMUSH's releases, newest first. Each GitHub Release tagged `vX.Y.Z` publishes the Docker images and must have a section here.

Two version numbers matter:

- **The engine version** is the release: what `version()`, `numversion()`, `@version`, MSSP's `CODEBASE` and a package's `requires_server` see. The `vX.Y.Z` tag sets it.
- **The plugin contract version** belongs to the `SharpMUSH.Library` and `SharpMUSH.Implementation.Generated` NuGet packages, which C# plugins build against, and is checked against a plugin package's `binaries.min_server_version`. It changes only when that contract does, and is released with a `plugin-nuget/vX.Y.Z` tag.

## [Unreleased]

### Added

- An application's data reply can answer `"shown": false`, and its widget then draws nothing for that character: no card, no empty state, no gap. The Application builder's widgets take **Who sees it** on the values step: every character, characters with a role, characters without a role, characters with a permission, characters without a permission, or characters who pass a lock key. It is checked against the character a profile or name card shows (on other layouts, the viewer), so a character sheet on profiles can skip staff with "Characters without a role: wizard". It is kept as the user lock ``APP`<SLUG>`` on the app's holder (#2937).
- `graph_components()` splits a graph into the groups its links join, whichever way the links point, so softcode can find separate clusters and nodes nothing links to (`help graph_components()`). `help graph_reach()` shows how to list every node, isolated ones included, by passing all of them as starts.
- Graph functions walk trees and graphs kept in attributes (`help graph functions`). Each takes a link function that returns what a node links to, and the engine keeps the visited set, the order and any loop. `graph_reach()` lists everything the starts lead to in `bfs`, `dfs`, `post` or `layers` order, with or without the starts, to a depth, one level per line or through a format function. `graph_path()` finds the way with the fewest links or, given a cost function, the lowest total, to the nearest of several targets. `graph_fold()` builds a result for each node from its children's (or, with `down`, its parents'), with an optional second value carried beside it, so one walk gives `tree()` a drawing with totals in it. `json_walk()` visits every node of a JSON tree under whatever key holds its children, with each node's level, place and JSONPath. A loop in a walk that cannot have one is named: `#-1 CYCLE A B A`.
- Avatars cross the Discord bridge. A line posted in Discord carries its speaker's portrait (the character's visual `IMAGE`, served from `mud_url`) as the webhook post's avatar; a member's line from Discord carries their Discord avatar when the character has no portrait. In the game, the portal shows a line from Discord with the character's portrait, else the member's Discord avatar (discord-channels 1.4.3). A picture Discord could not fetch (no `mud_url`, a private or local address) is left out. `FeedSend.Picture` gives a line the picture it came with from outside, which taps get as `%<picture>`.
- Staff set the order of the category cards on the portal's wiki home with **Wiki home order** on the wiki admin page (`/admin/wiki`): drag a pinned category or move it with its arrows, then **Save order**. A newly pinned category goes last, and `@wiki/pin` lists the pins in that order. The API is `PUT api/wiki/categories/pin-order` (wiki.admin), and `api/wiki/navigation` carries the order as `pinnedOrder`.
- `+compose` writes a mail message a line at a time from any client (bundled package `mail-composer` 1.0.0, offered ticked at setup). It asks who it is to and the subject, or takes them as `+compose <players>[=<subject>]`, then takes the message line by line, nothing in it evaluated, with `.proof`, `.edit`, `.insert`, `.delete`, `.to`, `.subject`, `.urgent`, `.send`, `.quit` and `.abort`. It sends as the player with `@mail`, so signatures and mail locks apply. The draft is kept on the character through `.quit`, a disconnect or the end of the session, and `+compose` goes on with it (#2553).
- Mail conversations. Every message has an id that all its copies share, however many players it went to, and belongs to a thread: a new message starts one and a reply joins the thread of the message it answers. `@mail/reply <msg>=<text>` answers the sender and `@mail/replyall <msg>=<text>` the sender and everyone they addressed (an alias stays an alias), under `Re: <subject>`; `/quote` adds the original below; both take a message's id in place of its number. A message number in `@mail`'s player list (`@mail 3=<text>`) replies as PennMUSH's does. `@mail/thread <msg>` or `@mail/thread <id>` lists a thread, each message in it you sent or received with each reply under the message it answers, and `mailthread()` returns a message's thread id. ``MAIL`RECEIVED`` passes the thread id as `thread`, and a reply reaches `MAILFILTER` with `R` in its flags. The portal's Reply and Reply all send in the thread, and a message's page shows its conversation laid out the same way. World format 3: mail already stored gets its ids when the server first opens the world, the copies of one send sharing one, and a 1.1 server then refuses the world.
- The portal's **client** (`/client`) is Play for several of your characters at once, opened from **Play several characters** at the end of Play's sidebar (shown to an account with more than one character). The client connects every one of the account's characters (up to 8) and the rail lists them, each with its unread count; a click brings one to the front, connecting it first when it is not, and the others stay logged in with their own output, channels, pages and unsent line. Another click can follow at once: a click made while a character is still coming to the front is played next, and of several only the last. A theme's entrance (cards rising in) plays when the page opens, not on each switch, and Play keeps its layout across a switch (a collapsed Here and Exits column stays collapsed instead of sliding shut again). Switching characters does not count against the sign-in rate limit. The page keeps the theme of the character the tab started with; the character in front shows its own theme on Play's card and widget column. `api/comm` takes `?character=<objid>` for any of the account's characters.
- Gallery moderation options, all off by default (`@config gallery`, #2879): `gallery_consent_text` asks every uploader to accept the game's terms and keeps who accepted them, when and the text with the image; `max_gallery_megabytes` limits the space a character's images take; `gallery_limit_skips_official` leaves official art out of both limits; `gallery_portrait_approval` makes a player's new portrait wait for staff, who approve, decline or clear portraits at `/admin/portraits` or in the image viewer (events ``GALLERY`SUBMIT`` and ``GALLERY`PORTRAIT``); `gallery_staff_only` leaves every gallery change to staff who hold `media.admin`. Staff can mark any image official art.
- A softcode package lists the commands it adds under `commands:` (package format 1.24): each names the command, the object and the attribute it runs. The installer adds and hooks them, the server adds them again on every start, and uninstalling removes them, so a package needs no `STARTUP` `@command/add` and `@hook`. The review screen lists them, and an apply naming a built-in command or another package's command is refused. The bundled packages with commands use it: achievements 1.1.0, alts 1.6.0, autoset 1.2.0, availability 1.8.0, bboards 1.11.0, casefiles 1.1.0, chargen 2.11.0, finger 1.8.0, health 1.5.0, info 1.6.0, jobs 1.21.0, multidescer 1.2.0, onboarding 1.4.0, plus-config 1.5.0, relationships 1.6.0, roster 1.7.0, scene-safety 1.7.0, softcode-editor 1.3.0, status 1.7.0, summary 1.4.0, time 1.9.0 and watch 1.7.0.
- Portal applications can follow the tab's play connection (plugin contract 4.1.0). A compiled component gets a cascading `IPlaySession` with who is playing, the connection, the room and the out-of-band packages the server sends that character, limited to the packages its application declares in `Subscribes`; a hosted page declares `subscribes` in its `ui.json` and gets the same events over its bridge (`play-subscribe`, `play-event`). `PlayPackage.Read<T>` reads a payload by its `"v"` version and never throws on extra, missing or mistyped fields. See `docs/design/play-events.md`.
- The `SharpMUSH.Implementation.Generated` analyzer package warns (`SHARPMUSH001`) when a compiled application names one of the engine's `sharp.*` packages in the play packages it reads, and points it to `IPlaySession.State` and the `PlayStateChanged` and `PlayReset` events, which carry the same data.
- The engine sends portal connections `sharp.play` with the character, its name and its room on login, on resume and on every move.
- `@message` and `message()` take `/say`, `/pose`, `/semipose` or `/emit` (in `message()`, `say`, `pose`, `semipose` or `emit` among its switches): the message is that kind of speech. The speaker, the enactor with `/spoof`, must pass the Speech lock of where they speak, which LOUD passes, and recipients hear it as a say, pose, semipose or emit rather than a `@pemit`, so `@listen`, ^-patterns and AUDIBLE objects treat it as speech.
- The Scene System's interfaces and models (`ISceneService`, `ISceneServiceBehavior`, `ISceneSystemBuilder`, the scene models) are in their own assembly, `SharpMUSH.Plugins.Scene.Abstractions`, shipped in `plugins/scene/` and packed as a NuGet package. A plugin that builds on the Scene plugin references that alone, not the plugin; `examples/plugins/scene-behavior` does. The plugin template describes the same split for a plugin of your own.
- The World and Discord plugins have interface assemblies too. `SharpMUSH.Plugins.World.Abstractions` carries `IWorldMaps`, which reads stored maps, places and where a room stands. `SharpMUSH.Plugins.Discord.Abstractions` carries `IDiscordClientHandler` for attaching to the bot's gateway client, `IDiscordMessages` and `IDiscordLinkedAccounts`. Each ships in its plugin's folder and is packed as a NuGet package.
- A plugin that names another under `dependencies` in its `plugin.json` resolves that plugin's assemblies from the other plugin's own load context, so it can use the other plugin's types: a plugin can add a Scene System behavior with `ISceneSystemBuilder.AddBehavior<T>()` (`examples/plugins/scene-behavior`). A plugin another loaded plugin depends on is not unloaded or reloaded under it, and a plugin whose declared dependency is present but did not load is not loaded either, with a reason naming that dependency (#2880).
- Play's terminal settings offer **Export log…**: it saves the last hour, day or week, everything saved, or two times you choose, as plain text or as a web page with the game's colours, with or without each line's time. With the saved log off it exports what the terminal holds now, and a warning mark says so.
- Preferences a player chooses for themselves follow them to every computer. A package declares preference groups in its manifest (`preferences:`, format 1.21): each group is kept on the account, shared by all its characters, or on each character, and each key has a type (text, number, integer, boolean, choice or json), a default and limits. The values are attributes, ``PREF`<PACKAGE>`<GROUP>`<KEY>``, that softcode reads and sets like any other. `api/preferences/{group}` reads, sets and resets the signed-in player's values for portal applications, and the portal's Settings has a Game preferences page.
- A `json` preference is stored with the version of its shape, `{"version":<n>,"value":<the JSON>}`, so a package (or the portal) that changes the shape can tell an older value and move it on. A json key declares its version with `version:` (format 1.23, 1 unless given); a value stored without one counts as version 1. `api/preferences` reports each json value's `version` and the key's `declaredVersion`, and a write may name `versions` to keep a value in its older shape. Play's channel groups are stored this way.
- `default()` reads an account's attributes, `#acct:<key>`, as `get()` does.
- An account's characters set and clear its attributes. An attribute staff lock with a write key or a `wizard` or `locked` flag (`@attribute/access/retroactive <attribute>=wizard` flags every copy) stays theirs.
- A write key (`@attribute/lock/write`) now decides who writes its attribute: failing it refuses the write, clear or flag change even to whoever controls the object. Only God and `game.override` pass every key.
- Theme packages (`kind: theme`, package format 1.22) ship portal themes: colours, style choices, a stylesheet and the pictures it shows. Installing one from Admin → Packages adds its themes for players to choose and staff to make the default, a new version replaces them, and uninstalling removes them. The review screen shows each theme with a swatch. Packaged themes are read-only in the Themes editor; duplicate one to change it.
- Play's echo and its Hide pages and Hide channel messages settings are kept on the account, as the preference group `portal.play`, so they follow the player to every computer and character; a tab open elsewhere picks up a change when it comes back into view. Values a browser kept before move to the account the first time it has none. The width, the input box's height and the panels stay per browser. No package may use the id `portal`.
- Play's **Alerts…** (terminal settings) keeps rules on the account that colour or style a line, or only each place a rule matched or one group of it, play a sound or raise a browser notification when a new line from the game matches whole words, contained text, a line start, a wildcard pattern or a regular expression, in every line or only pages, channel lines or the rest. Bold, italic, underline and strike-through are buttons beside the colour. Under Advanced, a rule can paint the text instead of tinting behind it, show other text in place of what it matched (`$1`, `${name}`), hide the line, or skip the rules after it. A frame alerts once: the page keeps the number of the last frame that alerted beside its resume point, so a reload or a reconnect that replays frames never alerts twice, and a restored screen is coloured but quiet.
- Alerts' **Try a line** reads the sample as other output, a page or a channel message, so a rule kept to pages or channels can be tried before it is saved.
- Channel groups on the portal's Play page: sidebar categories that fold their channels away and open as one view of all their lines, each run led by its channel's name and edged in its colour (picked per channel, or Auto), with a picker for the channel to talk on. Made, renamed and removed from the sidebar's Browse mode or the view's header; a folded group shows its channels' unread lines added together; kept on the account.
- Play's terminal settings menu has **Input shortcuts**: a function key or number pad key runs a command line, a short lead the player picks sends the rest of a typed line to a channel (never `:`, `;` or `"`), and a line starting with the escape character (`/` unless changed) skips the leads and goes as typed. They are kept on the account with Play's other settings (`portal.play`: `shortcuts`, `channel_leads`, `escape`), in the browser for a visitor not signed in.
- Play's channel, channel group and conversation views take several lines: the input box grows to Play's **Input lines** setting, Enter sends, Shift+Enter starts a new line, and each line goes to the view's channel or person as typed (#2893).
- scene 1.28.0: `+scene/invite <id>=<player>[,<player>...]` invites several players at once, answers for each, and tells each one they were invited, with the scene's title and time. `+scene/uninvite <id>=<player>[,<player>...]` withdraws invitations, and `+scene <id>` lists who is invited. Only invited players may RSVP to an invite-only scene. `scene(<id>,invited)` lists the invited players and `sceneuninvite()` withdraws one.
- scene 1.28.0: `+scene/schedule/private`, `/invite-only` or both make a scheduled scene private, invite-only or both in the command that creates it, so it is never readable or joinable by others first. The portal's Schedule form uses them.
- scene 1.28.0: `+scene/go` to an invite-only scene takes only its members, the players invited to it, staff who manage scenes and wizards, the same lock as joining it.
- `scenecreate()` takes `<public>` and `<joinpolicy>` arguments, stored with the new scene in the same write, so `+scene/schedule/private/invite-only` never shows the scene to anyone first.
- Apps can ask for a new scope, `scenes.read` ("Read your scenes" on the Allow an app page): with it, an app such as a desktop client reads the scenes its character can read through `api/scenes` (the lists, a scene's card and its log) and follows them live on `/hubs/scene`, by the same visibility rules as the portal. It cannot join, pose, move or edit, and an app acting for a wizard sees hidden scenes only when it was allowed `game` too. A token without the scope is refused with `insufficient_scope`.
- The live scene hub takes an app's token as `access_token` in the query too, as SignalR sends it from a browser. An app's connection closes when its token expires, and within a minute of the player revoking the app, the account being banned or the character being unlinked from it; such an app joins no further scene.
- Apps need not be registered by staff first: an app can name itself by an https address, its `client_id`, that serves a JSON description of it (OAuth Client ID Metadata Documents). The game reads it the first time a player is sent its way, only from a public internet address, and again at most once an hour. `oauth_app_policy` chooses what happens next: `open` (Allow all, the default) lets it ask at once, with "Not reviewed by staff" on the consent page; `review` (Approval process) holds it until staff allow it; `registered` (Whitelist & blacklist) accepts only apps staff register or allow. The portal's Apps page lists every app players have used in one list, says in plain words what each may do, and lets staff allow, block or forget it; registering an app is a button there, needed only for an app that keeps a secret. The page also sets the policy and `oauth_blocked_domains`; blocking an app or its domain stops its tokens at once. Under `review`, an allowed app whose description later asks for more, or renames itself, waits for staff again. At most 100 apps are not reviewed at once, 5 from one host. Such an app is always public (PKCE, no secret), sends codes only to its own host, a loopback address or its reversed-host scheme, and players still allow it only what they hold. The server's metadata says `client_id_metadata_document_supported` unless the policy is `registered`.
- The portal has an Upcoming Scenes widget (`UpcomingScenes`): the next scheduled scenes the reader may see, with when each starts and a link to the full schedule. Staff place it from Admin → Layout, on the home page, beside Live now or in Play's aside; `count` and `days` set how many scenes and how far ahead (#2881).
- The portal's Schedule scene form and a scene's Edit form choose "Only invited players may join" and invite players by name; the Edit form withdraws an invitation by closing its chip. A scene's page lists who is invited.
- `@oob[/supported][/noeval][/silent|/noisy] <players>=<package>[,<message>]` sends an out-of-band (GMCP or portal) message as a command, so softcode no longer wraps `oob()` in `think`. It takes `oob()`'s arguments, permission and delivery, with `/supported` for its fourth argument. It confirms as `@pemit` does, unless `/silent` or `silent_pemit`, and its output (`%>`) is the number of connections reached.
- `portal_logo_full` sets a full logo for the portal's Home, sign-in and setup pages and the page shown while the game starts; `portal_logo` stays the compact mark in the menu bar and tab. Empty uses `portal_logo`.
- `onboarding_guide_name` and `onboarding_guide_art` give the portal's guide the game's own name and picture in place of Sharpie: in its lessons, the welcome page, Home's side picture and the guide's labels. The identity step of Prepare for players edits both, with a preview.
- The portal's `index.html` carries the game's name, logos and guide as the server sends it, so a reload shows the game's own title, logo and guide from the first render rather than SharpMUSH's until the server answers. `/index.html` redirects to `/`.
- scene 1.29.0: a scene's poses underline the names of its members every time one is written, a name, an alias or the first word of a name with a space in it, live, in `+scene/recall` and in `+scene/log`. `+config scene/name-marks` chooses `underline` (the default), `bold` or `off`.

### Changed

- `oob()` envelopes to portal connections name the sender's objid in `"from"`, and `oob()` and `@oob` send packages under `sharp.` only for holders of the new `oob.engine` permission, which the wizard role allows, so staff code can correct what the engine sent.
- Play's longer log is now the saved log, **Save log in this browser**, and is on until the player turns it off.
- An uploaded SVG is read as XML before it is stored: one that is not well-formed, declares a DTD, or holds script, `foreignObject`, an event handler or a link to another site is refused. SVG files are served with a Content-Security-Policy that keeps them from running script when opened on their own.
- The help and the softcode skill write an account's reference as `account(<player>)`, since `ref` is the default field; `account(<player>, ref)` still works.
- The portal's Play page reads its play connection, comm feed and channel member lists through one per-character session (`CharacterSession`, held by the tab's `CharacterSessionRegistry`), the groundwork for keeping several characters connected in one tab. Nothing a player, admin or plugin sees changes.
- A private scene that is invite-only is hidden from the start, not only once it ends: only its owner, its members and the players invited to it see it, in-game, in the portal and in its room. An invited player sees a hidden scene as its members do. room-contents 1.4.1 and highlights 1.4.3 show it to the players invited to it.
- A player whose invitation to an invite-only scene is withdrawn loses their RSVP to it too; a seat they already took stays. Staff holding `scene.manage` see every scene in the game, as wizards do. Wizards see hidden scenes in the portal too: lists, a scene's page, its log and the calendar. discord-scenes 1.2.3 takes no Discord event for a hidden scene and removes one when a scene becomes hidden, running or not. A wizard watching a hidden scene in the portal gets its live poses.
- Unused `using` directives and redundant casts are removed across the C# projects. Nothing a player, admin or plugin sees changes.
- Unused `using` directives are removed from the web portal and its tests too, along with unused private parameters, dead assignments and `== true` comparisons. Nothing a player, admin or plugin sees changes.
- Five unused parameters are removed after checking each was not a missing feature: the Discord relay keeps a new webhook whatever happens to the caller, the wiki prerender's `x-default` is the bare page URL, the portal guide's local key already names the journey, `@lset` parses the wizard flag for everyone so the refusal can say why, and `@chzone` strips privileges without the flag service. Nothing a player, admin or plugin sees changes.
- Unused C# code is removed: the `SharpMUSH.Database.Models` records, unused helpers in the engine, server, portal, Lightning provider and language server, the portal's unused configuration-row view, and unused private members in product and test code. Nothing a player, admin or plugin sees changes.
- The filter points in the availability, health, profile-handler, scene, staff, summary, time and who-where packages pass `lattr()` straight to `chain()`, which already finds a bare attribute name on the calling object. Each package's patch version goes up; what they show is unchanged.

### Fixed

- The `#lambda` help (`help anonymous attributes`) and `help lockfilter()` show code that runs with `paren_groups` off: the call inside the lambda escapes its parentheses and commas, as `map(#lambda/name\(\%0\), #3 #12)`. Written unescaped, the lambda's first `)` closed the outer function.
- Hovering the open channel, page or scene in a sidebar keeps its highlight. The plain hover fill replaced it, so on themes that mark the current line with a solid block (Isekai, Real Robot and others) its name turned the colour of the row behind it.
- The Claude Code Stop hook's test runs turn TUnit's HTML report off, as CI does, so a full `SharpMUSH.Tests` run no longer builds a 776 MB JSON report after the last test, which got it OOM-killed in a 10 GB container though every test passed.
- A full `SharpMUSH.Tests` run no longer fails requests with NATS no-reply errors (#2785). The test hosts' notifier and options are plain classes instead of NSubstitute substitutes, which kept every call of the run (millions) and made blocking garbage collections take 4-9 s, longer than the 5 s request timeout; the test project uses server GC, as the server does, and raises the thread pool's floor as `SharpMUSH.Tests.Integration` does.
- The wiki home's category cards show the image of the category's own page when it has one, and the image of one of its newest pages only when it has none.
- A portal application section with set columns places every element by its span, side by side, as it does short fields: tables, labelled values, stat tiles and other display elements, and coloured-text and graph fields, no longer take a whole row each. Those columns fold to one in a widget too narrow for them, such as one in a profile's side column, as well as on a phone (#2932).
- Play's saved log keeps each line once across a reload: the frames the server replays after a reload that the page before had saved already are left out, and Play tries to write the lines still waiting as the page is hidden or closed (#2894).
- In the client (`/client`), the page theme's letterbox bars (Directive, Directive Light) stay out of the play area, so Play takes the full height whichever character is in front.
- The channel picker in a Play channel group opens a list in the theme's colours, light or dark, instead of the browser's own, which could leave its names unreadable.
- A package behaviour test waits for a `@wait 0` follow-up that reached the queue just after the runner's queue barrier, until it finishes, before the next step runs, and fails a step whose near-term `@wait`s have not settled within 10 seconds (#2775).
- The portal draws `rule()` with `"border":"heavy"` 2px thick, as a heavy box's border is, and thicker than a single rule (MarkupString 2.31.7, #2912).
- `lsearch()`, `nsearch()` and `@search` take a search class by any prefix PennMUSH takes, so `eobjects`, `ethings`, `eplayers`, `erooms` and `eexits` filter as their singular forms do instead of being ignored, and `type` takes `things`, `objects` and the other plurals. A class they do not know is refused with "Unknown search class." and a type with "Unknown type.", as in PennMUSH (#2919).
- An app registered at a loopback address (`http://127.0.0.1/…` or `http://[::1]/…`) may come back on any port, as RFC 8252 asks, so a desktop app listening on a port the system picks gets its code. `localhost` and every other address still has to match exactly. On a port the app did not register, the player is asked every time, even for an app allowed before.
- An HTML line in Play is matched by Alerts, searched and read to screen readers as the words it shows, not its tags.
- The portal's Play terminal tells the game what it is when it was connected before Play opened, as it is right after creating a character. `terminfo()` read `unknown ssl websocket 16color` there until the next login.
- A connect hook run by a portal login (Guest or a character) reads `terminfo()` as `SHARPMUSH-PORTAL` with its capabilities. The portal's terminal names itself on its first frame, so the connection has its terminal types before the login runs (#2896).
- `help` and `rendermarkdown()` write headings, bold text and inline code in theme colours (`tone()`'s `strong` and `info`) instead of fixed white and pale blue, so they read on a light portal theme and in each player's `@theme` (#2875).
- `help cmdlink()` says to pad a link outside it, `ljust(cmdlink(Look,look),20)`, so only the label is clickable (#2873).
- room-contents 1.4.2: a player a wizard `@tel`'d into the wizard's own room gets the new room's `room.info`, so the portal's Play page shows the room and its scenes; it went to the wizard instead. ``ROOM`CONTENTS`` names what moved as `<mover>` on move-in and move-out.
- The package batch page keeps a run's results on screen after a package change makes the tab read its permissions again; it cleared them, so a refused step vanished without a word. A refused uninstall says why, in the installer's words.
- The portal's theme chooser lists the game's own themes as soon as they load, not only after its card is reopened.
- A command's restrictions and lock are checked before any `@hook` runs, as PennMUSH does: a GAGGED player can no longer `say`, `pose`, `;` or `@emit` through an `/override` hook (the scene package hooks all four), and `@command/restrict` holds for a hooked command.
- `WHO <pattern>` lists only the players it names, as `DOING` and `SESSION` do: a prefix of the name, or with `*` or `?` a wildcard over names and aliases (at the connect screen, a prefix of the name only). The footer still counts everyone. `DOING` is laid out as `WHO` is, with the same footer (`There are 2 players connected.`), which also counts the players its pattern skips.
- `WHO`, `DOING` and `SESSION` list the newest connection first, as PennMUSH does.
- A line break, tab or other control character in `@doing` is shown as a space in `WHO` and `DOING`, so each player stays on one line. The attribute keeps it.
- A browser component from an installed plugin package is served again: `api/plugins/<id>/ui/<assembly>` read the shipped plugins' folder instead of the installed one (`SHARPMUSH_PLUGINS_PATH`, or the world path plus `.plugins`), so it answered 404 (#2874).
- With `NATS_URL` unset, the socket server starts NATS in Docker itself, built or published, and shares one container with the main server whichever starts first; without Docker it stops at startup saying to set `NATS_URL` (#2729).
- Play's focus mode takes the shell's rail, header and side zones away again, and on a phone Play's card header is the one bar again, on `/play` and in the client (`/client`).
- In the client (`/client`), a character theme whose background drifts (Jovian) stays inside the play area, so the page no longer scrolls sideways and down when that character is in front.

## [1.1.1] - 2026-11-23

### Added

- A player without a `TZ` of their own is in their account's: `time()`, `timefmt()`, `convsecs()` and `convtime()` given a player read its `TZ`, then `#acct:<key>/TZ`, and `dateparse()` with no zone reads the caller's the same way. `timefmt()`, `convsecs()` and `convtime()` now take an object, a player or `#acct:<key>` as their zone, as `time()` does. The new `timezone(<object>)` names the zone in use, reading `TZ` as `get()` does (`#-1 NO PERMISSION TO GET ATTRIBUTE` when it may not), and `hasflag(#acct:<key>/<attribute>, <flag>)` reads an account attribute's flags. See `help timezones`.
- time 1.8.1: `+timezone` keeps a player's zone on their account, shared by every character on it, and a character may have its own, which comes first (`+timezone/account`, `+timezone/character`). `+config time/zone-store` chooses `both` (the default), `account` or `character`. A player on no account keeps it on the character. jobs 1.20.1, scene 1.26.1, health 1.4.1, info 1.5.1 and availability 1.7.1 read a zone with `timezone()`, so they find one kept on the account.
- bboards 1.10.2: what each player has read, left, follows and chose is kept on their account, so every character on it shares them. Where a character is reading and its drafts stay on the character, and a player on no account keeps them on the character. `+config bboards/read-store=character` keeps them per character instead. An update from an earlier bboards copies each character's marks to its account once, keeping the furthest any of its characters read.

### Changed

- The bundled packages that call `timezone()` require SharpMUSH 1.1.1 (`requires_server: ">=1.1.1"`), the first release that has it: time 1.8.1, bboards 1.10.2, jobs 1.20.1, scene 1.26.1, health 1.4.1, info 1.5.1 and availability 1.7.1.

## [1.1.0] - 2026-11-23

Plugin contract 4.0.0. World format 2: a 1.0.x world is moved to format 2 when 1.1.0 first opens it, and a 1.0.x server then refuses it, so take a `@backup` before upgrading if you may want to go back.

### Added

- The `multidescer-app` package, bundled and not installed by default: a portal page at `/apps/descs` where a player sees what they wear now, lists their pieces by slot and their outfits, writes, changes, wears and deletes them, and sets a short description. It runs the same routines as `+desc`, `+wear` and `+remove` (multidescer 1.1.0, which serves its routes). Text written there is kept as written unless the player ticks that it is code. A board shows each of the game's slots with what is worn in it, a slot that hides another drawn on top of it, and a four-step guide at `/apps/descs/guide` explains pieces, slots, hiding and limits with the player's own slots. A slots page at `/apps/descs/slots` moves, adds, renames and takes away the player's slots and sets what each hides and holds.
- Portal stat tiles take a `stack`: neighbouring tiles sharing one are drawn one above the other in one place.
- `renderplayers(<obj>/<attr>, <text>[, <count>[, <players>[, <prefix>[, <options>]]]])` replaces the player names in a text with what an attribute returns for each (`%0` the dbref, `%1` the name as written, `%2` the whole match), keeping the text's markup. Names match as whole words, ignoring case, by full name and alias. `<count>` is how many times each unique match (a name or an alias, in any case) is replaced (1 by default, 0 for every time, -1 to return the text unchanged); `<players>` limits it to a list of dbrefs; `<prefix>` (such as `@`) makes a name match only right after it; the options `noalias` and `first` (first names) change what matches. See `help renderplayers()`.
- Dynamic application forms have a `textart` field type, a text box in a fixed-width font whose lines do not wrap, for text art.
- Dynamic application forms have an `image` field type: a picture's address with a preview, and the media library's picker and upload for readers who may use them.
- The `achievements` package (1.0.0, with `achievements-help`, `achievements-config`, `achievements-finger`, `achievements-app` and `achievements-profile`), bundled and not installed by default. Staff holding the new `softcode.achievements.admin` permission make plaques with `+achievements/create <name>=<description>`, give them a text and background colour with `+achievements/colour <plaque>=<text>/<background>` (a pair needs a 4.5:1 contrast, so it reads in every colour vision) a style (bold, italic, underline) with `+achievements/style <plaque>=<styles>`, a typeface on the website with `+achievements/typeface <plaque>=<typeface>` (the theme's title or monospace face, or serif, sans or script), optional CSS of its own with `+achievements/css <plaque>=<declarations>`, and award them with `+achievements/award <player>=<plaque>[/<citation>]`; nothing is awarded automatically. An award, who gave it, its citation and the plaques a character features are kept on the character in `ACHIEVEMENT` attributes only wizards write; the plaques themselves are on a store object. `+achievements [<player>]` shows a character's plaques. `+achievements/feature <plaque>` picks up to three held plaques (`+config achievements/featured`), which `achievements-finger` shows as the Plaques field on `+oocfinger`. `achievements-app` is the Achievements page at `/apps/achievements`, a row of plaque pills with each description on hover, where staff make, change, award, take back and destroy plaques, and `achievements-profile` shows a character's plaques as pills at the bottom of their profile page.
- A portal chips element's entry can be a pill with its own look: `{ text, background, foreground, style, typeface, css, hint, link }`. The two colours are `#rrggbb` and go together, `style` is any of bold, italic and underline, `typeface` is the theme's title or monospace face or serif, sans or script, `css` is optional declarations the portal filters (no colour, face, position or anything loaded), `hint` shows on hover and focus and is the pill's accessible description, and `link` opens a portal page.
- The `multidescer` package (1.0.0, with `multidescer-help` and `multidescer-config`), bundled and not installed by default. `+desc/save <name>=<text>` saves a description and `+desc <name>` wears it, as on RhostMUSH and PennMUSH multi-descers; `+desc/save <slot>/<name>=<text>` saves a piece in a slot (body, hair, top, feet, outer and so on), and `+wear` and `+remove` change one piece and keep the rest. Pieces are put together in slot order into `DESCRIBE`; a slot can cover others and limit how many are worn. `+desc/outfit` saves what is worn as an outfit. A character's existing description is saved as `original` the first time. `+shortdesc` sets a one-line `SHORTDESC`. `+config multidescer` sets the slots and limits.
- multidescer 1.1.0: players own their slots. `+desc/addslot`, `+desc/slot <slot>/<setting>=<value>` (name, after, paragraph, hides, max) and `+desc/delslot` change them, and the first change copies the game's list onto the character; `+desc/resetslots` goes back to it. `+config multidescer` sets the list players start with and `max-slots`. A whole description can hold a slot's place with a `<slot>` marker, where the pieces worn in that slot are read. A slot cannot hide one that already hides it, and a slot taken away, by a player or from the game's list, hands what it hid to the slots that hid it.
- plus-config 1.4.0: a system's `ACONFIG` gets `%<removed>` when a table entry is removed, the entry's other fields as they were, as a JSON object of strings.
- The `scene-rooms` package (1.0.0, with `scene-rooms-config`; scene 1.25.0) runs a scene in a temporary copy of the room you stand in. `+scene/create/copy <title>` and `+scene/start/copy [<id>]` make the copy, bind the scene to it and take you there; others follow with `+scene/go`, and those left in the room are told. The copy takes the room's `DESCRIBE`, `DESCFORMAT`, `CONFORMAT` and `EXITFORMAT` and its parent, never map data (`MAP`, ``MAP`**``, `ENVIRONMENT`, `AREA`, the zone), and has one `out` exit back. It belongs to the Scene Logger's owner, is MISTRUST, and is removed when the scene ends, has been paused a week, or is 30 days old. `+config scene-rooms` sets what is copied (include and exclude patterns), the exit, the caps, the day limit and the paused time. In the portal, the Scenes start form has **Run it in a copy of the room I'm in**, a scene's page has **Start in a copy of the room I'm in**, and Play's empty Scenes group links to the form.
- `finger-profile` (1.0.0), a bundled add-on joining finger and profile-handler: once installed, a character's portal profile is their `+finger`: the in-character fields, read as `+finger` shows them to whoever is looking, in place of the Identity section (created date and objid). A field the player hid shows only to them and staff, and the `+oocfinger` fields stay in the game. `+config finger/portalhide` leaves fields off the portal. profile-handler 1.3.0 adds the filter points it uses, ``FILTER`PROFILE`SCHEMA`<NAME>`` and ``FILTER`PROFILE`DATA`<NAME>`` on the HTTP handler, and finger 1.7.0 shows a reader who is not signed in what everyone may read: a field that is visual and not kept from mortals.
- Private wiki pages: a page whose members, characters or roles, each a reader, contributor or lead, are the only ones besides `wiki.admin` who see it, in every listing, search, function and portal page. `@wiki/create/private` makes one, `@wiki/member` lists and sets its members, `wikimembers()` and `wikimember()` read them, and `@wiki/access` marks one. `@wiki/insert` puts text first under a heading, and `/quiet` leaves out the line saying a `@wiki` change was done. The world format moves to 2, so an older server refuses a world with private pages instead of showing them to everyone.
- Case files, the bundled `casefiles` package: `+casefile` opens a private wiki page per plot in the Case Files category, lets characters and roles in, and posts dated developments to it, running `@wiki` as the player. `casefiles-scene` files scenes into a case file and names it on the scene's card to its members; `casefiles-app` is the portal page at /apps/casefiles; `casefiles-help` puts the topics in `+help`.
- Account attributes: each account keeps attributes on `#acct:<key>`, which `account(<player>, ref)` returns. It is no object and runs no code; `&`, `@set`, `@atrlock`, `@wipe`, `@cpattr`, `@mvattr`, `@edit`, `@atrchown`, `examine`, `get()`, `xget()`, `lattr()`, `nattr()`, `hasattr()`, `lflags()`, `set()`, `attrib_set()` and `wipe()` reach it. `players.moderate` writes them; `players.view` and the account's characters read them; attribute flags and `@attribute` apply as on an object. `examine #acct:<key>` shows the account's username (to `players.view`), characters and attributes, and `@decompile #acct:<key>` writes its attributes back by reference. The portal's Softcode Editor opens one from a search for `account(*<name>, ref)`. A database import keeps them with the accounts. A world from a `dev` build that stored account buckets moves each bucket to the account attribute of the same name when it opens (world format 2); a bucket whose name is not a valid attribute name, or whose attribute already exists, stays where it was and the server logs a warning.
- Attribute keys: staff with `config.admin` give a standard attribute a read key and a write key in the attribute table, with `@attribute/lock/read` and `/write <attrib>=<key>` (without `=` it shows the key; an empty key takes it off). Whoever passes the read key may read that attribute on every object, and whoever passes the write key may set or create it, without controlling the object; a key never takes access away, and attribute flags still apply. The nearest key up the attribute tree applies. A write key never clears the attribute or changes its flags; clearing and `@wipe` still need control. `@attribute <attrib>` shows the keys to `config.admin` and `@attribute/decompile` writes them. On an account a `role^<role>` key lets a role write that attribute, and an evaluation key never passes. The portal's Configuration has an Attribute keys page under Security.

- Attribute flag changes (`@set obj/attr=<flags>`) parse the flag list into one list in flag table order, checked against privileged names as it is read, instead of a parse step, three privileged-flag checks and a batch record carrying the flag table to the report. Behaviour is unchanged.

- The portal's Here card on Play lists your own character too, first, ringed in the accent colour and labelled "you".

## [1.0.3] - 2026-11-18

The 1.0.2 release published no images, because its tagged source had no 1.0.2 section in this changelog. 1.0.3 is the first release whose images carry 1.0.2's changes as well as these. Plugin contract 4.0.0. World format 1: a 1.0.0, 1.0.1 or 1.0.2 world opens as it is.

### Added

- The wiki editor says under the source box, and `help wiki line breaks` explains, that lines next to each other join into one paragraph and how to keep a line on its own (end it with `\` or two spaces).
- `+scene/go <id>` (scene 1.23.0) takes you to the room a running scene is in. A scheduled, paused, finished or cancelled scene is refused, and so is a FIXED character; it needs `scene.join`. In `+scene` a running scene's room is a link to it, and in the portal the room name on a running scene's card, page and live view is a button that goes there and opens Play.
- `wsjson(<json>[, <default>])`, PennMUSH's: a WebSocket connection such as the web portal is sent the JSON as `{"type":"json","data":…}` after the line, on the path `oob()` uses, and every other reader sees `<default>` in its place. Only the server changes.
- The play terminal's input box takes several lines: it grows with what you type, for code and long poses, up to the **Input lines** setting in its settings menu (5 by default), then scrolls. Enter still sends and Shift+Enter starts a new line; each line is sent as its own command, as a MUD client sends a paste. Up and Down move between the box's lines and walk the command history once the caret is at the start or the end. Kept per browser.
- The World map's builder mode asks before throwing away changes not yet applied: leaving the page, opening another map, Back, **Discard changes**, and closing or reloading the tab (the browser's own prompt). While changes wait, the page header shows **Review and apply** beside **Discard changes**, so the review is no longer only at the foot of the builder panel.
- The portal's **Your scenes** list has **Start now** on a scheduled scene (and **Resume scene** on a paused one) for its owner or a holder of `scene.manage`, so a scene starts without opening it first. It runs `+scene/start` as the acting character.

### Changed

- `scene` 1.21.0: `+scene/leave` makes a player inactive. They stay on the scene's cast while it has a pose of theirs, and come off it only with none, or only deleted ones; before, a deleted pose still kept them on. The owner can't leave their own scene: `+scene/leave` only makes them inactive, as `+scene/deactivate` does, and the Play page shows them **Go inactive** in place of **Leave scene**.
- A private scene runs like any other: it shows in its room, anyone there may join it, and its owner and cast pose in it. Once it is finished or cancelled, only those who took part (and wizards) see it, in `+scene/mine` and their own lists. `scene(<id>,hidden)` is 1 for such a scene. Scene package 1.22.0, room-contents 1.3.3, highlights 1.4.2.
- A room running several scenes shows each on its own row under **In scene** on the Play page, and each row opens that scene's Story; before, the page showed only the most recent. A pose made in the room goes to the scene there you are focused on, whichever is most recent. `scenelist(room[, <room>])` lists every active scene in a room, and `scenewhere(<room>, <player>)` answers the one there that player is focused on first. Each row marks whether you are active in that scene, with a green check and **Active**, or a grey circle and **Inactive** or **Not joined**. room-contents 1.4.0 sends them all as `scenes` in `room.info`.
- An ordinary `pose`, `say` or `@emit` is refused while the scene you are active in runs in another room, so it is neither said here nor recorded there; `+scene/pose <id>=<text>` still poses into it from anywhere. A pose into your scene while another active scene in the room had a pose more recently still goes to yours, and warns you which one, in case you are in the wrong scene. Scene package 1.24.0.
- `cmdlink()` needs no power: any room, object or player can make a command link. `tagwrap()`'s SEND and XCH_CMD parameters, `sound()`, `image()` and the other client-control functions still need a Wizard or Send_OOB. `@function/restrict cmdlink=game.wizard game.send_oob` puts the old gate back.
- The Play page's Story composer offers Emit, OOC, Pose and Command, with Emit first and chosen by default. Say is gone; a draft kept as Say opens on Emit with its text.
- `messages` 1.4.2: the connect screen's text logo is drawn with `tone(primary,...)` instead of a fixed `ansi(#00f5b7,...)`, so it takes the reader's `@theme` or the game's `layout_theme` colour. Under the default `sharpmush` theme that is its primary teal, `#00bf8f`. A blank line now separates the welcome from the commands under it, in the object and in the stored connect text.

### Fixed

## [1.0.0] - 2026-11-14

The first release. Plugin contract 4.0.0. World format 1.

### The server

- A MUSH server on .NET 11 that aims at PennMUSH compatibility: the softcode parser, commands, functions, flags, locks, attributes, zones, parents, the queue, `@mail` and channels.
- Imports a PennMUSH database and its `mush.cnf` from the setup wizard. Colour codes that cannot be converted safely are removed, with a warning. Differences from PennMUSH are listed in `help pennmush compatibility`.
- Stores the world in an embedded LMDB database (the `lightning` provider): one directory per world, no database server to run. `@backup` copies a live world without stopping it; `@storage` reports space and history retention.
- Three processes: the game server, a socket server that owns client connections and keeps them across game server restarts, and a rendering worker. NATS connects them. The socket server and the rendering worker are native binaries, compiled ahead of time. The Compose files in `deploy/` run the set.
- Telnet with TTYPE, CHARSET, MSSP, GMCP, MXP and Pueblo; WebSocket clients; ASCII output for clients without UTF-8, and a screen-reader mode.
- Styled text is MarkupString, rendered for each client's protocol and width. Listings and panels follow the game's `layout_border` and `layout_theme`.
- Roles and permissions in place of fixed wizard and royalty bits, managed with `@role`. Secrets are stored encrypted and never readable from softcode.
- Softcode packages (`package.yaml`) installed, upgraded and rolled back from the portal. 110 packages are bundled with the server, counting each system's help, configuration and portal packages. Among them are jobs, bulletin boards, scenes, chargen, a wiki reader, `+who`/`+where` and the onboarding tutorial.
- C# plugins built against the plugin contract: Discord, Scene, World (grid maps), a language server for softcode and an MCP server are bundled.

### The portal

- A web portal served by the game server: account sign-in, characters, a terminal, scenes, mail, a wiki with semantic facts, a softcode editor, and administration for configuration, roles, packages, backups and moderation.
- A setup wizard on first boot: claim the admin account, import a PennMUSH world, choose handlers and the bundled packages.
- Themes, including built-in genre, anime, console and tabletop role-playing game, fan-game setting, game-menu, creature-game and Chinese history themes, and staff stylesheets. Any theme can mix how menus mark the current line, button shapes, card materials, meters, motion and atmosphere.

### Upgrading

- There is nothing to upgrade from. Worlds written by development builds from before 6 October 2026 cannot be opened.
- A world is stamped with its format. A server refuses a world stamped newer than its own.
- Requires the .NET 11 runtime. The Docker images carry it.
